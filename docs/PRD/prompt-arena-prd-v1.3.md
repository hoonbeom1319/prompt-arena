# 프롬프트 아레나 (가칭) — PRD (Product Requirements Document)

> **버전:** v1.3 (MVP, 운영 피드백 3차 반영)
> **작성일:** 2026년 6월 (v1.0) / 갱신: 2026년 6월 (v1.1~v1.3)
> **상태:** 소규모 운영 중 (제출자 ~20명). 데일리 O/X 퀴즈 추가 + admin 출제 방식 현실 반영.

---

## 0. 이 문서를 읽는 법

이 문서는 1인 풀스택 개발자가 만드는 *AI 프롬프트 경진대회 서비스* MVP의 PRD입니다. 다음 원칙으로 작성되었습니다.

- **기능은 최소로, 구조는 확장 가능하게.** 모든 결정이 이 원칙을 통과했습니다.
- **결정에는 근거가 따라옵니다.** 6개월 뒤 *"왜 이렇게 정했지?"* 떠올릴 때 답을 주기 위해 근거를 같이 적었습니다.
- **빠진 것도 명시합니다.** Out of Scope와 Phase 2 섹션이 진짜 PRD의 절반입니다. 무엇을 *안 하는지*가 무엇을 하는지만큼 중요합니다.
- **이 서비스는 "행위의 기록"이 데이터의 본질입니다.** 장소·정보 같은 정적 데이터가 아니라 *생성했다·제출했다·투표했다*라는 시간 기반 행위가 중심이라, 시각(timestamp)과 상태 전이가 설계의 핵심입니다.

### 0.1 v1.1 변경 요약 (운영 피드백 1차)

소규모 운영 중 *"투표 단계에서 출품작이 많아 하나하나 보기 힘들다"*는 피드백을 받아 다음을 반영했습니다. (상세는 4.6 참고)

- **생성 횟수 5회 → 3회** 로 확정 (비용 절감 + 충분한 다듬기 기회). 문서 전체 일관화.
- **투표 피로도 완화 3종 (공평성을 깨지 않는 범위):**
  1. *전수 노출 유지 + 노출 순서 랜덤화* (앞쪽 편향 방지).
  2. *"전부 볼 필요 없음 — 마음에 드는 것에만 3표" UI 명시.*
  3. *AI 중립 요약*(평가 아닌 색인. 제출 시 1회 생성·저장. 기본 표시·접기 가능).
- **AI가 출품작을 *거르는* 1차 필터링은 거부** (판정자 자리에 AI를 앉히지 않음 — 공평성·정체성 충돌).
- **1:1 비교(페어 투표)는 Phase 2 트리거**로 보관 (소규모 표본에선 순위 불안정).

### 0.2 v1.2 변경 요약 (운영 피드백 2차 — 주기 단축)

*"3일 한 바퀴가 느리다, 다음 챌린지를 빨리 하고 싶다"*는 피드백 + 제출자 ~20명(콜드 스타트 탈출)을 근거로 다음을 반영했습니다. (상세는 4.5 참고)

- **3일 주기 → 2일 주기:** *제출 1일 + 투표·결과 1일.* 투표 마감(자정) 직후 즉시 결과(순위·코인) 공개.
- **일정: 월~토 2일씩 주 3챌린지 + 일요일 휴식** (운영자 쉬는 날 보장 — 1인 운영 지속성 우선).
- **전제(타협 불가): 주기 단축은 *출제 부담 제거*와 세트.** AI 출제를 *승인제*(완성형 후보를 AI가 뽑고 운영자는 선택·승인)로 강화 + *주제 1~2주치 배치 비축.* 이게 없으면 주기 단축이 운영자 번아웃으로 직결되므로 *선행 조건.*
- **블라인드는 그대로 유지:** 투표 3표 → *프롬프트* 즉시 열람(학습). *순위·득표는* 투표 마감 후 공개(밴드왜건 방지). — 이건 변경이 아니라 *재확인.*
- **주기 단축이 안전한 이유:** 제출자 ~20명이라 2일 주기로 챌린지가 잦아져도 *챌린지당 성립선(5명)*을 유지. (소규모였다면 위험했을 결정.)

### 0.3 v1.3 변경 요약 (운영 피드백 3차 — 빈 시간 채우기 + 출제 방식 현실화)

2일 주기 전환 후 남은 *(B) "제출하고 나면 (투표·결과까지) 할 게 없다"* 빈 시간 문제를 풀기 위해 **데일리 O/X 퀴즈**를 추가합니다. (상세는 4.7 참고)

- **데일리 O/X 퀴즈 (작은 미니게임):** 하루 1문항(상식·프롬프트 작성법). *연승* 시스템으로 매일 올 이유 제공. 챌린지는 격일, 퀴즈는 매일 → *데일리 리텐션* 보강.
- **범위 엄격 한정:** 퀴즈는 *양념*이지 본체가 아니다. 별도 리더보드·상점·카테고리 없음. 연승 숫자 + 간단한 뱃지(10·20·30연승)까지만.
- **연승 규칙:** *하루라도 빠지면 연승 초기화* (틀려도 초기화). 데일리 리텐션의 긴장감.
- **퀴즈 코인 보상 (폭발 방지):** *매일 소액 + 연승 마일스톤(10·20·30…) 보너스.* "n승=매일 n개"는 *지수 폭발·부익부·본질 추월* 때문에 거부. **두 원칙 고정: ① 마일스톤 보너스에 상한 ② 퀴즈 누적 보상 < 챌린지 우승 보상(양념이 본체를 못 넘는다).**
- **신규 데이터 축 인지:** 연승 = *일별 사용자 기록*이 생김 → 출석 추적 레이어가 사실상 생김(출석 뱃지도 가능해짐).
- **신고 기능 / 제출 시 콘텐츠 사전필터:** 요구는 접수했으나 **이번 사이클 홀딩**(우선순위 밀림). 미해결 이슈로 보관(11.2).
- **admin 출제 방식 현실 반영 (챌린지·퀴즈 공통):** AI를 *admin 내부에서 호출하지 않는다.* 운영자가 *외부 AI 도구(Claude 프로젝트, Gemini Gems, ChatGPT 등)에서 대화로 만들고* admin엔 *완성본을 등록(입력)만.* "사람이 최종 게이트"라는 승인제 정신은 유지, 구현은 단순화.

## 1. 배경과 문제 정의

### 1.1 배경

AI 프롬프트 엔지니어링이 현대인의 필수 역량이 되었지만, 두 가지가 어렵다.

1. **쓸 만한 프롬프트를 *찾기* 어렵다.** (탐색/큐레이션 문제)
2. **내가 짠 프롬프트가 잘 짠 것인지 *비교·검증·학습*하기 어렵다.** (평가 문제)

이 둘은 서로 다른 문제다. 경진대회+투표 포맷은 (2)를 직접 푸는 도구이고, (1)은 (2)로 쌓인 결과물이 누적되며 *부산물*로 따라온다.

### 1.2 핵심 문제

> 내가 짠 프롬프트가 잘 짠 것인지 *가늠할 기준*이 없다. 더 잘한 프롬프트가 뭐가 다른지 *비교·검증*할 무대가 없다.

같은 과제라도 누가 더 좋은 프롬프트를 짰는지 *공정하게 겨루고 검증*하는 장이 없다는 것이 본질이다.

### 1.3 서비스의 정체성

- **재미있는 3일 챌린지 + 투표를 엔진 삼아, 질 좋고 검증된 프롬프트를 카테고리별로 누적하는 서비스.**
- **장기 목적지:** "이런 상황엔 어떤 프롬프트?"를 검색해 *우승(검증된) 프롬프트*를 찾는 아카이브 + 그 위의 수익모델.
- **MVP의 일:** 그 아카이브의 *재료를 쌓는 엔진*(챌린지 + 투표)을 재미있게 작동시키는 것. **검색·수익화는 재료가 충분히 쌓인 Phase 2.**
- **닭이 먼저다.** 쌓인 게 없으면 검색할 것도 없다. 그래서 MVP는 *검색*이 아니라 *쌓는 엔진*이다.
- **시스템은 판정하지 않는다.** 우열은 *사람의 투표*가 가린다. AI는 보조(요약·출제 초안)일 뿐 *심사위원이 아니다.* (4.6 참고)

## 2. 목표와 성공 지표

### 2.1 진짜 목표

> 질 좋고 검증된 프롬프트를 *지속적으로 누적*한다. 장기적으로 이 아카이브를 검색 서비스로 키우고 수익을 만든다.

수익은 (다)로 지향하지만, **MVP의 성공 지표로 삼지 않는다.** 대신 *"수익이 언젠가 얹힐 토대(사람이 모이고·머물고·다시 오는가)가 깔리는가"*를 본다.

### 2.2 측정 가능한 지표

**핵심 지표 (이 서비스가 본질을 하고 있는가)**

- **챌린지 성립률**: 한 챌린지가 *제출자 5명 이상*으로 마감되는 비율.
  - 목표 초안: *운영자 시드를 제외한 순수 사용자 제출만으로 70% 이상.*
  - 운영상 두 가지를 따로 본다: ① *시드 포함 성립률*(화면이 비지 않는가) ② *순수 사용자 성립률*(진짜 살아나는가).
  - 근거: 제출 5명이 안 되면 투표도 학습도 굶는다. 1순위 생존 지표.
- **제출 → 투표 전환**: 한 챌린지에서 제출 또는 투표한 활성 참여자 중 *투표 3표를 다 쓴* 비율.
  - 목표 초안: *50% 이상.*
  - 근거: 투표가 본질. 들어와 구경만 했는지 *실제로 참여했는지*를 본다.

**성장 지표 (서비스로 자라고 있는가)**

이 서비스는 2일 주기로 도니, *주 단위가 아니라 챌린지 단위*로 재방문을 본다.

- **챌린지 간 재참여율**: 이번 챌린지 참여자가 *다음 챌린지에도* 참여하는 비율. 목표 초안: *30% 이상.*
- **신규 → 2회차 잔존**: 처음 참여한 사람이 *두 번째 챌린지*까지 오는 비율.

**건강 지표 (토대가 멀쩡한가)**

- **운영자 시드 의존도**: 전체 제출 중 운영자 시드가 차지하는 비율. *낮아질수록 성공.* (안 떨어지면 "사람이 안 모인다"는 위험 신호 → 13장 연결)
- **AI 주제 적격률**: AI 초안 챌린지 주제 중 운영자가 *수정 없이 통과*시킨 비율. (낮으면 출제 AI 프롬프트 개선 필요, 운영 부담 직결)
- **투표 도달 분포 (v1.1 추가)**: 출품작별 *받은 노출/표가 고르게 분산되는가.* 특정 작품만 표가 쏠리거나 일부가 노출조차 안 되면 *노출 균등화·투표 방식 재검토* 신호. (4.6의 피로도 완화책이 공평성을 안 깨는지 점검하는 지표.)

**측정 까다로운 것 (지표 후보로만 보관)**

- **학습이 일어났는가**: 직접 측정 불가. *재참여자의 제출이 이전보다 더 많은 표를 받는가*(실력 향상의 대리지표)를 데이터가 쌓이면 관찰.

### 2.3 지표 운영 원칙

- 위 숫자는 *기준선*이지 정답이 아니다. 운영하며 조정.
- 측정 불가능한 목표("실력을 키운다")가 아니라 *행동의 흔적*으로 환산한다.

## 3. 타깃 사용자

### 3.1 핵심 통찰 — 제출자(생산자)는 항상 소수다

거의 모든 경진/UGC 서비스에서 *콘텐츠를 생산하는 사람*은 소수(보통 1:9~1:99)다. 따라서 **"제출자(고수)를 어떻게 확보하느냐"가 서비스 생사의 9할**이다. 투표자는 상대적으로 모으기 쉽다. *생산자가 귀하다.*

### 3.2 핵심 사용자

**1번 사용자 (MVP 핵심 = 제출자): AI를 실무·취미로 자주 쓰는 중상급~고수**

- 프롬프트에 자기 나름의 노하우와 자부심이 있고, *그게 통하는지 검증받고 싶은* 사람.
- **동기:** 익명·블라인드 무대에서 *순수 실력으로 1등을 증명*하고, 그 증명을 코인·뱃지·랭킹이라는 *눈에 보이는 숫자로 박제*하는 것.
- 근거:
  1. **콜드 스타트는 콘텐츠 품질로 깬다.** 텅 빈 서비스에 감탄할 프롬프트가 있어야 사람이 남는다. 초기엔 양보다 질이 사람을 붙잡고, 그 질의 원천은 고수다.
  2. **메인 목표가 "질 좋고 검증된 프롬프트 누적"** — 그 질의 원천이 고수다.
  3. **이탈 방지.** 입문자를 타깃으로 잡으면 매번 깨져서 상처받고 떠난다. 고수는 *이기려고* 남고, 입문자는 *구경·학습*하러 부담 없이 온다.

**2번 사용자 (동시 존재, 화면 우선순위 낮음 = 투표자): AI에 관심 있는 입문~중급자**

- 직접 내긴 부담스럽지만 *구경하고 투표하며 배우고 싶은* 사람.
- 제출자의 콘텐츠에 *끌려와* 투표자로 참여, 코인을 모으고, 일부는 나중에 제출자로 자란다.
- **v1.1 주의:** 이 사용자가 *투표 피로*를 느끼면 이탈한다. 투표 경험의 가벼움(4.6)이 이 사용자 유지의 핵심.

### 3.3 "별풍선" 통찰 — 코인·뱃지·랭킹의 1차 가치

초기 고수가 텅 빈 서비스에 첫 프롬프트를 내는 동기는 *코인/상금*이 아니다(쓸 데도 자랑할 사람도 없으므로). 진짜 동기는 **"내 프롬프트가 남들 것보다 낫다는 걸 *눈에 보이는 표로* 증명받고 싶다"**는 **사회적 인정 욕구**다.

> 코인·뱃지·랭킹의 1차 가치는 "현금화"가 아니라 **"실력이 숫자로 증명되는 사회적 인정의 가시화"**다. 현금화(수익)는 나중에 얹는 두 번째 동력이다.

출력 블라인드 투표(결과물만으로 평가)는 이 욕구를 정확히 채운다 — 순수하게 결과로 1등을 먹으면 그건 *운이나 인맥이 아닌 실력의 증명*이다.

### 3.4 재미의 정의

- **(가) 경쟁·랭킹의 재미** (내가 몇 등인가) + **(다) 성취의 재미** (코인·뱃지·우승).
- **(나) 발견의 재미** (남의 기발한 프롬프트 구경)는 Phase 2 검색 아카이브와 함께 자연히 따라온다.

### 3.5 콜드 스타트 (빈집 문제) 대응

- **출시 전 제출자 확보:** 첫 챌린지 성립(*제출자 5명*)을 위해, *구체적으로 섭외 약속을 받은 사람*을 미리 확보 (본인 + AI 잘하는 지인 직접 섭외 + 부족분 운영자 시드). 막연한 "퍼지겠지"가 아니라 *손에 잡히는 개별 섭외.*
- **서비스 내 신원 표시:** *전원 익명/닉네임.* 출력 블라인드 평가 정신과 일관. (운영자의 비공개 섭외 명단과 서비스 표시는 다른 층위.)
- **홍보(투표자·확산):** MVP에선 *지인·관련 커뮤니티(개발자 채널, AI 오픈채팅 등) 직접 알리기* 수준으로 최소화. 본격 확산은 콘텐츠가 쌓이는 Phase 2의 일.

## 4. 기능 요구사항

### 4.0 핵심 메커니즘 (모든 기능이 매달린 척추)

**A. 제출 메커니즘**
- 한 사용자는 한 챌린지에서 프롬프트를 *최대 3회 생성·시도*할 수 있다(각 시도 = Gemini 1회 실행).
- 시도한 것 중 *1개를 선택해 제출*한다.
- **제출은 확정 잠금** (수정·삭제 불가).

**B. 실행의 공정성**
- 모든 제출의 결과물은 **시스템이 Gemini API로 동일 조건(모델·온도·래퍼 텍스트 고정)으로 실행**한다.
- 실행 조건이 다르면 투표가 *실력*이 아니라 *운 좋은 출력*을 평가하게 되므로, 조건 고정은 타협 불가.

**C. 순차 진행 (페이즈 모델) — 제출과 투표는 시간으로 분리된다**
- 제출 기간엔 투표가 닫혀 있고, 투표 기간엔 제출이 마감된다.
- 이 페이즈 분리가 **베끼기를 원천 차단**한다(제출 중엔 아무도 못 보고, 투표 중엔 봐도 더 못 낸다). 따라서 *개인별 잠금 규칙은 불필요* — 페이즈가 자동 해결.

**D. 출력 블라인드 투표**
- 투표 기간엔 *결과물만* 보인다. 프롬프트 본문과 작성자는 가려진다.
- *투표 중 득표수·순위는 숨긴다* (밴드왜건/쏠림 방지). 종료 후 공개.

**E. 프롬프트 공개(학습 재료 해제) 규칙**
- 투표 3표를 다 쓰면 → 그 챌린지의 *전체 프롬프트 열람 해제* (나).
- 챌린지 종료 시 → *전체 공개* (다).
- 미제출 생성 시도는 *본인만* 열람(타인에게 절대 비공개).

**F. 투표**
- 챌린지당 *최대 3표.*
- *자기 출품작에도 투표 가능* (단, 3표 한도에 포함 — 보너스표 아님. 전원에게 동일하게 열려 있어 체계적 편향 없음).
- **전부 볼 필요 없음 (v1.1):** 투표자는 *마음에 드는 것에만* 3표를 쓰면 된다. 전수 정독은 의무가 아니다. (4.6 참고)

### 4.4 기능 명세 (상세 동작)

#### F-1. 챌린지 조회 / 첫 화면
- 첫 화면 = **지금 진행 중인 챌린지 하나**를 크게 보여준다 (목록형 아님).
  - 근거: 본질이 "지금 이 챌린지에 참여하라". 고르게 하면 에너지 낭비 + 초기엔 고를 것도 없음.
- 첫 화면은 **현재 서버 시각 기준 상태에 따라 4개 뷰로 분기**한다(아래 F-2).
- 목록·지난 챌린지는 *부가 동선*(별도 화면).

#### F-2. 첫 화면 — 상태별 4뷰 분기

| 들어온 시점 | 보여주는 것 | 핵심 행동 |
|---|---|---|
| **제출 기간** | 주제 + 참가자 수 + 마감 카운트다운 + *내 제출 상태* | [프롬프트 만들기] / [내 제출 보기] |
| **투표 기간** | 주제 + 출품작 리스트(결과물만, 블라인드, 순서 랜덤) + *내 투표 상태(N/3)* | [투표하러 가기] |
| **결과 (투표 마감 후 / 종료)** | 주제 + 최종 순위 + 우승작 + *전체 프롬프트 공개* | [결과 보기] |
| **공백(일요일 등)** | 진행 중 챌린지 없음 → 지난 결과로 안내 | [지난 결과 보기] |

- **로그인/비회원 분기:** 비회원은 주제·출품작·결과 *구경 가능*. 단 [만들기]·[제출]·[투표]를 누르면 *로그인 유도.* 로그인 사용자에게만 *"내 상태"*가 얹힌다.
- **제출 기간 화면 비어 보임 방지:** 타인 출품작·프롬프트는 비공개로 막되, *주제·참가자 수·남은 시간·내 상태*로 채운다. (표현 디테일 — 스켈레톤/카운터 등 — 은 디자인 단계, 9장 참고.)

#### F-3. 프롬프트 생성 화면 (가장 공들여야 하고 돈이 나가는 화면)
- 구성: *주제 표시 + 프롬프트 입력 + [실행] + 결과물 표시 + 남은 횟수(N/3) + 재시도 + 제출 선택.*
- 사용자가 프롬프트 입력 → [실행] → 시스템이 *서버 경유*로 Gemini 호출 → 결과물 표시 (1회차).
- 마음에 안 들면 다시 입력·실행 (최대 3회). **3회 소진 시 생성 잠금.**
- **3회 한도는 서버가 카운트해 막는다** (API 비용 방어선).
- **실행 실패(API 에러) 시 횟수 차감하지 않음** (사용자 잘못 아님 + 항의 CS 방지). *성공했으나 결과가 불만족인 경우는 차감.*
- **(v1.1) 제출 시점 요약 생성:** 제출이 확정되면 그 결과물에 대한 *AI 중립 요약*을 1회 생성·저장한다 (4.6.4). 투표 화면은 저장된 요약을 읽기만 한다.
- 엣지: 예산 한도 도달 시 — 4.0/10장/13장의 예산 정책에 따라 *정직한 안내* ("선착순 마감" 등 오해 문구 금지).

#### F-4. 제출 확정
- *3개 생성 시도 중 1개 선택* → [제출].
- **확정 경고 모달**: *"제출하면 수정·삭제할 수 없어요. 계속할까요?"* → 확인 시 잠금.
- 확인 시 *AI 중립 요약 생성·저장*을 트리거 (F-3 / 4.6.4).
- 제출 후 첫 화면은 "제출 완료" 상태로.
- 한 사용자는 한 챌린지에 *최대 1개 제출.*

#### F-5. 투표 (투표 기간)
- 출품작 리스트 = *결과물만* 표시 (프롬프트·작성자 가림).
- **(v1.1) 노출 순서 랜덤화:** 매 투표자마다 리스트 순서를 섞어 *앞쪽 편향*을 막는다. (4.6.1)
- **(v1.1) 카드 구성:** *AI 중립 요약(기본 표시) → 펼치면 전체 결과물.* 요약은 *접기 가능* (원문으로만 판단하고 싶은 사용자 배려). (4.6.4)
- **(v1.1) 안내 문구:** *"마음에 드는 것에만 투표하세요. 전부 볼 필요 없어요."* — "다 읽어야 한다"는 압박 제거. (4.6.2)
- 출품작 탭 → 상세에서 결과물 정독 → [이 작품에 투표] → 1표 소진.
- 최대 3표. *자기 출품작에도 투표 가능*(3표에 포함).
- **3표를 다 쓰면 → 그 챌린지 전체 프롬프트 열람 해제** (나). 이후 각 출품작의 프롬프트까지 보며 학습.
- *투표 중 득표·순위 숨김.*
- 서버는 매 투표 요청 시 *서버 시각으로* "투표 기간인가 + 3표 미만인가"를 재판정.

#### F-6. 결과·순위 (투표 마감 후 / 종료)
- 최종 순위 + 우승작 + *전체 프롬프트 공개* (다).
- 우승작 상세 → 결과물 + 프롬프트 전체 → 학습.
- 우승 프롬프트 [공유] → *고유 URL 복사* (아카이브 씨앗 + 확산).
- 제출자는 *내 순위·득표·획득 코인* 확인.
- 종료 시점에 득표를 집계해 *Submission에 최종 득표·순위를 스냅샷으로 고정*하고 코인을 지급한다.

#### F-7. 인증 (로그인)
- **소셜 로그인 + 이메일 로그인** (Supabase Auth 통합).
- *이메일 가입 시 인증 메일 확인*을 거친다 (다중계정·봇 일부 방지).
- 생성·제출·투표는 *로그인 필수.* 비회원은 구경만.
- 행동 시도 시 로그인 게이트 → 로그인 후 *원래 보던 화면·행동으로 복귀.*

#### F-8. 코인 (적립 전용)
- *우승*과 *활동(제출·투표 등)*으로 적립. 신규도 활동으로 모을 수 있어 부익부 완화.
- **MVP는 적립만.** 사용처 없음(Phase 2). *명성·랭킹 점수*로 표시.
- 모든 적립은 원장(CoinTransaction)에 기록.

#### F-9. 뱃지·랭킹
- **MVP 뱃지(전부 기존 기록으로 산출 가능):** 첫 제출 / 첫 우승 / 우승 N회 / 투표 N회 / (선택) 챌린지 연속 참여 N회.
- *일회성*(첫 제출·첫 우승)과 *누적형*(N회)으로 구분. 누적형은 Submission·Vote 기록에서 카운트.
- **출석 기반 뱃지는 Phase 2** (3일 주기와 안 맞음. 일별 방문 기록도 현재 모델에 없음).
- 랭킹: 코인·우승 횟수 등으로 산출 (구체 산식은 운영하며 조정).

#### F-10. 카테고리·태그 (Phase 2 씨앗)
- 챌린지에 *카테고리* 1개를 부착(드롭다운). 필요 시 태그.
- MVP에선 *검색·탐색 기능 없음.* 단 모든 챌린지에 메타데이터를 *처음부터* 달아둔다 (나중에 소급 태깅은 지옥).

#### F-11. 링크 공유
- 결과·우승 프롬프트 화면에서 공유 → *고유 URL 클립보드 복사.*
- 받은 사람이 *앱 설치 없이 웹*에서 바로 진입.

### 4.5 일정·페이즈 명세 (서비스의 시계) — v1.2 (2일 주기)

```
1일차 00:00 ~ 23:59   제출 (주제 공개 + 생성·제출)
2일차 00:00 ~ 23:59   투표 (출품작 공개, 블라인드 투표)
2일차 23:59 (마감)     → 즉시 결과 공개 (순위·우승·코인 지급)
                        (전체 프롬프트는 종료로 완전 공개)
```

**주간 배치 (월~토 2일씩 3챌린지 + 일요일 휴식):**

```
월·화   챌린지 1 (월 제출 / 화 투표 → 화 자정 결과)
수·목   챌린지 2 (수 제출 / 목 투표 → 목 자정 결과)
금·토   챌린지 3 (금 제출 / 토 투표 → 토 자정 결과)
일      휴식 (새 챌린지 없음, 지난 결과 열람, 다음 주 주제 예고)
→ 주 3챌린지
```

- **주기:** 2일 주기, 주 3챌린지. (v1.0~v1.1의 3일 주기에서 단축. 사유: "느리다" 피드백 + 제출자 ~20명으로 성립선 안전.)
- **결과 타이밍:** 투표 마감 직후 *즉시* 순위·코인 공개. 별도 "결과일"을 두지 않고 *투표일 자정에 흡수.* 결과 음미는 *다음 챌린지 제출일과 공존*(20명 규모면 "할 게 항상 있다"는 긍정 효과).
- **프롬프트 열람 vs 순위 공개 (재확인):** 투표 3표 소진 시 *프롬프트는 즉시 열람*(학습 가능). *순위·득표는 투표 마감 후*에만 공개(블라인드·밴드왜건 방지). 두 개념은 다르다.
- **주제 예고:** 각 챌린지 *결과 시점(투표일 자정)*에 다음 챌린지 주제 예고. 일요일에 다음 주 첫 주제 예고. "결과 = 다음 예고" 규칙 유지.
- **일요일 휴식:** 운영자 쉬는 날 보장. *1인 운영의 지속 가능성이 서비스 생존보다 우선*(운영자가 멈추면 서비스도 멈춤).

**출제 부담 제거 (주기 단축의 선행 조건 — 타협 불가):**
- 2일 주기 = 주 3챌린지 = 출제·검수가 잦아짐. 주기를 줄이기 *전에* 출제 부담을 없애야 운영자 번아웃을 막는다.
- **AI 출제 승인제:** AI가 *완성형 주제 후보*를 여러 개 생성 → 운영자는 *좋은 것을 클릭 승인*(작문이 아니라 선택). (A-3 참고)
- **주제 배치 비축:** 한 번에 *1~2주치* 주제를 승인해 큐에 쌓아둠. 매 챌린지 출제가 아니라 *가끔 배치 작업*으로 전환.

- **비상 탈출구 (유지):** 운영이 버거우면 *3일 주기 또는 주 2챌린지로 즉시 완화*, 더 버거우면 *7일 주기.* 주기는 시각 설정값이라 변경 용이. (13장 위험 신호 연결.)

### 4.6 투표 피로도 완화 (v1.1 신설)

> **배경:** 소규모 운영 중 *"투표 단계에서 출품작이 많고 결과물이 길어 하나하나 보기 힘들다"*는 피드백. 핵심 통찰 — 출품작이 임계치를 넘으면 *수가 100이든 200이든 똑같이 막막*하다. 따라서 *출품작 수를 줄이는 게 아니라, 출품작 수와 무관하게 투표자 1명의 부담을 일정하게* 만드는 것이 목표.

> **대전제 (타협 불가):** 어떤 완화책도 *공평성·블라인드·"시스템은 판정하지 않는다"* 정체성을 깨지 않는다. 그래서 **AI가 출품작을 거르는 1차 필터링은 거부**한다 (4.3). AI가 탈락을 정하면 그 작품은 *사람 표를 받아볼 기회조차* 잃는다.

#### 4.6.1 노출 순서 랜덤화 (MVP, 채택)
- 전수 노출은 유지하되, *매 투표자마다 출품작 리스트 순서를 무작위로 섞는다.*
- 목적: "맨 앞 작품만 표를 받는" 위치 편향 제거. 전수를 보여주므로 공평성은 유지.

#### 4.6.2 "전부 볼 필요 없음" UI (MVP, 채택)
- 진짜 통증은 *물리적 불가능*이 아니라 *"전부 정독해야 할 것 같은 압박"*이다.
- 투표 화면에 *"마음에 드는 것에만 투표하세요. 전부 볼 필요 없어요"*를 명시. 3표만 쓰면 끝.

#### 4.6.3 1:1 비교(페어 투표)는 Phase 2 트리거 (보류)
- 출품작이 *아주* 많아져도 *개인은 몇 쌍만* 비교하면 되는 방식(LMArena/Elo류). 출품작 수와 부담을 완전히 분리.
- **단, 소규모 표본에선 순위가 불안정**(어떤 작품은 한두 번만 비교 → 운에 좌우). 투표자 풀이 출품작 수를 충분히 웃돌 때 진가.
- **도입 트리거:** *한 챌린지 출품작이 투표자 수에 비해 과도하게 많아지고, "다 못 본다"는 피드백이 재발*할 때 검토. 멈춤 기준은 *수요일 자정 마감*(개인당 비교 N회 한도 + 종료 시각 집계).

#### 4.6.4 AI 중립 요약 (MVP, 채택) — "평가 아닌 색인"
- **목적:** 긴 결과물을 *읽기 전에 빠르게 파악*해 훑는 속도를 높임. *우열 판단은 사람에게 남김.*
- **경계 (핵심):**
  - *허용(묘사):* 무엇을 다뤘는지, 접근/구조, 길이·톤·형식. (예: "단계별 설명형, 약 300자, 격식체")
  - *금지(평가):* 좋다/나쁘다, 잘/못, 점수, 추천, 우열 암시 일체. ("잘 썼다/인상적/아쉽다" 류 금지)
  - 요약 생성 *시스템 프롬프트*에 *"너는 평가자가 아니라 색인 작성자다. 가치판단·우열·칭찬·비판 금지, 객관적 특징만 묘사"*를 명시.
- **왜 점수가 아니라 요약인가:**
  - AI 점수는 *앵커링*(사람이 점수에 끌려 투표 쏠림 → 블라인드·독립 판단 붕괴, 실시간 순위를 숨긴 이유와 동일).
  - 점수는 *우리가 평가하려는 바로 그 대상(프롬프트 우열)을 AI에 위임*하는 순환. ("AI가 좋아하는 프롬프트 = 좋은 프롬프트"는 불확실.)
- **타이밍/비용:** *제출 확정 시점에 1회 생성·저장.* 투표 화면은 저장본 읽기만(추가 호출 0). 예산 게이트에 *제출당 요약 1호출* 포함.
- **표시:** 카드에 *요약 먼저 → 펼치면 전체 결과물.* **요약은 기본 표시, 사용자가 접을 수 있음**(원문으로만 판단하고 싶은 고수 배려).
- **엣지(우아한 실패):** 요약 생성 실패 시 *요약 없이 결과물만* 표시. 투표는 정상 작동. 요약은 어디까지나 보조.

### 4.7 데일리 O/X 퀴즈 (v1.3 신설) — "빈 시간 채우는 작은 미니게임"

> **배경:** 2일 주기 전환 후에도 *(B) "제출하고 나면 투표·결과까지 할 게 없다"* 빈 시간 문제가 남음. 챌린지는 격일이라 *매일 올 이유*가 부족. 데일리 O/X 퀴즈로 빈 시간을 채우고 매일 방문 동기를 만든다.

> **대전제 (범위 한정 — 타협 불가):** 퀴즈는 *양념*이지 본체가 아니다. 본체는 *프롬프트 경진*. 퀴즈가 화면·보상·관심의 무게중심을 가져가면 본질이 흐려진다. 그래서 *작게* 가둔다 — 별도 리더보드·상점·퀴즈 카테고리 *없음.* 연승 숫자 + 마일스톤 뱃지까지만.

#### 4.7.1 기본 동작
- **하루 1문항.** 주제: 상식 또는 *프롬프트 작성법.* 형식: O/X (정답 명확한 것만).
- 사용자가 O 또는 X 선택 → *즉시 정답 + 해설* 공개. (1초 마찰, 부담 0.)
- 로그인 사용자만 응답·연승 집계 (비회원은 구경/체험만, 연승 미집계).
- **하루 기준 = 서버 시각 자정~자정** (모든 시각은 서버 기준 원칙과 일관).

#### 4.7.2 연승 (Streak)
- *연속 정답일수*를 집계. 사용자의 *성취 가시화*(별풍선 계열) — 진짜 보상은 코인이 아니라 *연승 숫자 그 자체.*
- **초기화 규칙: 하루라도 빠지면 연승 0으로 초기화. 틀려도 초기화.** (데일리 리텐션의 긴장감. 운영자 본인의 타 서비스 경험에서 작동 검증된 방식.)
- 연승 마일스톤(10·20·30…)에 *뱃지* 부여.

#### 4.7.3 코인 보상 (폭발 방지 설계)
- **매일 정답 시 소액(예: 1코인) + 연승 마일스톤(10·20·30…) 도달 시 보너스 한 번.**
- **거부된 안: "n승 = 매일 n개".** 사유:
  - *지수 폭발* (30연승이면 누적 1+2+…+30=465, 하루에만 30개).
  - *부익부* (고인물이 기하급수 독식 → "코인=평등한 인정"이라는 2단계 결정과 충돌).
  - *본질 추월* (O/X 한 번 탭이 챌린지 우승 코인보다 커지면 사람들이 챌린지 대신 퀴즈만 함).
- **고정 원칙 2가지 (운영 중에도 사수):**
  1. *마일스톤 보너스에 상한* (예: 30연승까지만 보너스, 이상은 매일 기본만). 100·200연승에서 재폭발 방지.
  2. **퀴즈 누적 보상 < 챌린지 우승 보상.** 양념이 본체를 못 넘는다.
- 구체 수치는 *예시*이며 운영하며 조정. 단 위 두 부등호/상한은 고정.

#### 4.7.4 출제 (admin 외부등록 방식 — 챌린지와 동일)
- 운영자가 *외부 AI 도구(Claude 프로젝트, Gemini Gems, ChatGPT 등)에서 O/X 문항 + 정답 + 해설을 묶음(예: 한 달치)으로 만들고*, admin에는 *등록(입력)만* 한다. 매일 손출제 아님 — *배치 비축.*
- **정답 검수 필수:** O/X는 정답이 명확해야 함. *논쟁 여지 있는 프롬프트 기법*(예: "프롬프트는 길수록 좋다")은 피하거나 *해설로 근거를 명시.* AI 생성이므로 *운영자 검수가 신뢰의 핵심* (정답 틀리면 서비스 신뢰 손상).

#### 4.7.5 데이터/엣지
- **신규 데이터 축:** 연승 집계 = *일별 사용자 응답 기록*이 필요 → "데일리 리텐션 레이어"가 새로 생김. (출석 뱃지가 사실상 가능해짐 — Phase 2에서 활용 가능.)
- 하루 1문항 *재응답 불가* (한 번 풀면 그날은 끝).
- 문항 재고 소진 대비: 비축이 떨어지면 *그날 퀴즈 없음*(연승은 "출제된 날"만 카운트하도록 — 출제 공백이 사용자 연승을 깨지 않게). ※ 운영 시 비축 잔량 모니터링.

## 5. 관리자 페이지 요구사항

### A-1. 관리자 인증
- 사용자 인증(소셜/이메일) 재사용 + User의 *관리자 여부* 속성으로 권한 식별.

### A-2. 대시보드
- 진행 중/예정 챌린지 상태, 새 출품 현황, 예산 사용량(월 $100 대비), 빠른 진입 [챌린지 출제] [시드 제출].

### A-3. 챌린지 출제 (외부 AI 작성 → admin 등록) — v1.3 현실 반영
- **AI를 admin 내부에서 호출하지 않는다.** 운영자가 *외부 AI 도구(Claude 프로젝트, Gemini Gems, ChatGPT 등)에서 챗봇과 대화하며* 챌린지 주제(제목·지시문)를 완성하고, **admin에는 *완성본을 등록(입력)*만 한다.**
  - 근거: admin 내 AI 호출은 구현·비용·유지보수 부담. 외부 챗봇은 이미 쓰는 도구라 *대화로 더 정교하게* 다듬을 수 있고 admin은 *입력·관리*만 하면 됨. "사람이 최종 게이트"라는 승인제 정신은 그대로.
- **주제 배치 비축:** *1~2주치*를 미리 등록해 *예약 큐*에 쌓아둠. 매 챌린지 출제가 아니라 *가끔 배치*로 채워 자동 게시.
- 입력 필드: 주제(제목 + 지시문), 카테고리(드롭다운), 챌린지 유형(MVP: 단독생성형 고정), 제출/투표 시각, 실행 조건(모델·온도 — 기본값 자동 채움), 예고 시각.
- 출제 시 *예산 게이트* 통과 확인 (A-7 참고).
- 채점 가능한(우열이 갈리는) 주제인지 운영자가 최종 판단. — 큐레이션 = 손맛. *최종 게이트는 사람.*

### A-4. 시드 제출 (콜드 스타트)
- 운영자가 챌린지에 *시드 출품작*을 직접 추가해 빈집 방어.
- 시드 출품작도 *제출 시 AI 중립 요약을 동일하게 생성*(투표 화면 일관성).
- *시드를 예시로 표시할지 / 자연스럽게 섞을지*는 미해결 이슈(11장)로 관찰.

### A-5. 출품작·결과 모니터링
- 진행 중·종료 챌린지의 출품작(결과물) 목록 조회.
- 부정 출품(욕설·도배 등) *직접 삭제* (별도 제보 화면 없이 운영자 모니터링으로 갈음).
- 종료 후 순위·득표 확인.

### A-6. 사용자·코인 관리
- 사용자 목록, 닉네임/상태, 코인 잔액·적립 내역 조회.
- 필요 시 수동 조정(예외 대응).

### A-8. 데일리 퀴즈 관리 (v1.3)
- 외부 AI로 만든 *O/X 문항 + 정답 + 해설*을 *배치 등록*(예: 한 달치). 게시 일자/순서 관리.
- 등록 시 *정답·해설 검수*(논쟁 여지 없는 명확한 문항인지). 비축 잔량 표시.

### A-7. 예산 관리
- 월 예산 상한 $100 대비 *현재 사용량* 표시. 80% 도달 시 *운영자 알림.*
- *새 챌린지 열기 전 예산 게이트*: 남은 예산이 한 챌린지 풀(예: 최대 제출자 수 × (3회 생성 + 1회 요약)) 이상인지 확인. 부족 시 신규 챌린지 보류.

### 6.3 설계 원칙

- **챌린지 상태는 저장값이 아니라 시각으로 계산한다.** `상태` 필드를 직접 저장·관리하면 1인 운영자가 제때 못 바꿔 데이터가 거짓말을 한다. *4개 시각만 저장하고 현재 서버 시각과 비교*해 제출중/투표중/결과를 매번 계산하면 시간이 흐르며 자동 전이된다. (`상태` 필드를 둔다면 캐시용으로만.)
- **시각의 진실은 항상 서버.** 모든 제출·투표 요청은 *서버가 자기 시각으로* 기간·한도를 재판정해 허용/거부. 클라이언트 시간은 *카운트다운 표시용*으로만(서버 시각 동기화). 사용자가 브라우저 시간을 바꿔도 판정에 영향 없음.
- **득표수는 투표 중엔 Vote에서 계산(숨김), 종료 후 Submission에 스냅샷 고정.** 진실의 원천은 Vote 기록.
- **생성 시도 전부 저장 + 미제출은 본인만 열람.** 장기적으로 *프롬프트 개선 과정* 데이터 자산이 됨. 미제출 비공개는 베끼기 방지와도 일치. (저장 비용은 텍스트 한정으로 억제.)
- **AI 중립 요약은 Submission에 저장한다 (v1.1).** 제출 시 1회 생성. 투표 시 재호출 없음. 실패 시 빈 값 허용(우아한 실패).
- **코인은 적립 전용(MVP).** 사용처를 안 만들어 *화폐 밸런싱 늪*을 회피. 데이터 모델은 사용(-)도 가능하게 열어두되 MVP에선 +만.
- **닉네임은 UUID 식별 + 중복 허용 + 표시 꼬리표.** 유니크 강제 없이 가입이 막히지 않으면서, 표시 시 동명이인 혼동을 식별자 꼬리표로 해소.

## 7. 사용자 흐름

### 7.1 시나리오 ① — 제출자(고수)의 제출일

```
앱 열기 → [첫 화면: 제출 기간 뷰] 주제 확인
  → [프롬프트 만들기] (비회원이면 로그인)
  → 프롬프트 입력 → Gemini 실행 → 결과물 확인  (1회차)
  → 불만족 → 다시 입력·실행  (2~3회차, 3회 소진 시 잠금)
  → 3개 중 1개 선택 → [제출] → 확정 경고("수정·삭제 불가") → 잠금
  → (시스템) AI 중립 요약 생성·저장
  → [첫 화면] "제출 완료" 상태로 복귀
```

### 7.2 시나리오 ② — 투표자의 투표일

```
앱 열기 → [첫 화면: 투표 기간 뷰] 출품작 리스트(결과물만, 순서 랜덤)
  → 안내: "마음에 드는 것에만 투표하세요. 전부 볼 필요 없어요."
  → 출품작 카드: AI 중립 요약(기본 표시, 접기 가능) → 펼치면 전체 결과물
  → 마음에 드는 작품 [투표] (비회원이면 로그인) → 1표 소진
  → 비교, 최대 3표
  → 3표 다 쓰면 → 그 챌린지 전체 프롬프트 열람 해제(나)
  → 각 출품작 프롬프트까지 보며 학습
```

### 7.3 시나리오 ③ — 종료 후 결과·학습

```
투표 마감(자정) → [첫 화면: 결과 뷰] 최종 순위 + 우승작
  → 우승작 탭 → [출품작 상세] 결과물 + 프롬프트 전체 공개
  → "이 프롬프트가 왜 1등인지" 학습
  → 우승 프롬프트 [공유] → 고유 URL 복사
  → (제출자라면) 내 순위·득표·획득 코인 확인
```

### 7.4 로그인 후 복귀 흐름

```
비회원이 [만들기]/[제출]/[투표] 시도
  → [로그인 게이트] 소셜/이메일
  → (이메일이면 인증 메일 확인)
  → 콜백 후 *원래 보던 화면·행동으로 복귀*
```

- **첫 화면은 현재 시각 기준 상태로 렌더링** (제출/투표/결과/공백 4뷰).
- **로그인 후 복귀**: 항상 *로그인 직전 보던 화면·행동*으로.
- **링크 진입(고유 URL)**: 해당 결과/우승 프롬프트 화면 직접 렌더링. 비회원도 구경 가능.

## 9. 디자인 방향

### 9.1 톤

- **경쟁의 긴장감 + 신뢰감.** 실력을 겨루는 무대이므로 *집중되고 또렷한* 톤. 동시에 *공정성·투명성*이 느껴지게(블라인드·정직한 안내).
- **성취의 가시화.** 코인·뱃지·랭킹·순위가 *눈에 보이는 보상*으로 또렷하게 드러나야 함 (별풍선 통찰).

### 9.2 화면별 디자인 메모

- **제출 기간 화면이 비어 보이지 않게**: 참가자 카운터, 남은 시간, 스켈레톤 등 *기대감·긴장감을 주는 장치* 검토. (규칙은 "타인 출품작 비공개", 표현은 디자인 단계에서.)
- **생성 화면**: 남은 횟수(N/3), 실행 로딩, 결과물, 재시도, 제출 선택이 한 흐름으로. 3회가 *소중하게* 느껴지도록.
- **투표 화면 (v1.1)**: 블라인드(결과물만) 강조. 득표·순위는 *숨김*이 디자인으로도 분명히. *AI 요약은 카드 상단에 작고 차분하게*(평가가 아니라 색인임이 톤으로 드러나게 — 점수처럼 보이지 않게). 요약 *접기/펼치기* 토글. "전부 볼 필요 없음" 안내를 부담 없는 톤으로.

### 9.3 디바이스 우선순위

- **모바일 웹 우선.** 데스크톱은 관리자 페이지 위주(반응형 가능 범위까지).

### 9.4 다크모드

- **MVP 미지원.** 출시 후 요청 모이면 검토.

## 10. 비기능 요구사항

### 10.1 성능
- 첫 화면 로딩: 모바일 환경에서 빠른 첫 콘텐츠 표시.
- *생성(Gemini 실행)*은 비동기 — 로딩 상태를 명확히 표시(수 초 소요 가능).
- *AI 요약*은 제출 시 비동기 생성 — 제출 흐름을 막지 않음(저장 완료 전이면 투표 화면에서 요약 없이 표시).

### 10.2 보안 / 프라이버시 (이 서비스의 핵심 비기능)
- **Gemini API는 반드시 *서버 경유*로 호출** (Supabase Edge Function 등). 프론트 직접 호출 금지 — API 키 노출 차단. *요약 생성 호출도 서버 경유.*
- **모든 기간·한도 판정은 서버 시각·서버 데이터로.** 클라이언트 시간/입력 불신.
- 사용자 데이터 최소 수집 (인증 식별자 + 닉네임 + 활동 기록).
- 이메일 가입 시 *인증 메일 확인.*
- 약관·개인정보 처리방침 *출시 전 게시 필수.*

### 10.3 비용 방어 (Gemini 예산)
- **키 1개 + 우리 서비스가 호출 수를 카운트해 통제** (Generation 기록으로 산출).
- **챌린지 단위 예산 게이트:** 새 챌린지 열기 전 *남은 월 예산 ≥ 한 챌린지 풀(최대 제출자 수 × (3회 생성 + 1회 요약))* 확인. 부족 시 신규 챌린지 보류 — *진행 중 챌린지는 영향 없음(시작한 경기는 끝까지 보장).*
- **콘솔 월 상한 $100 + 80% 도달 시 운영자 알림** — 코드 통제가 뚫려도 막는 *최후 안전망.*
- **저가 모델(Flash 계열) 고정**으로 단가 억제. *요약도 저가 모델·짧은 출력으로 비용 최소화.*
- **그럼에도 한도 도달 시: 사용자에게 *정직한 안내*** ("선착순 마감" 등 오해 문구 금지. 예: "지금은 생성 요청이 많아 잠시 어려워요. 다음 챌린지에서 만나요.").
- 정교한 호출별 예약(reservation)은 *Phase 2 최적화.* MVP는 챌린지 단위 게이트로 시작.

### 10.4 데이터 무결성
- 제출은 *확정 잠금* (수정·삭제 불가).
- 카테고리/실행조건 등은 *미리 정한 목록·고정값*에서 선택.
- 시드 반영·관리자 조정 등 데이터 변경은 운영자 확인 절차.

### 10.5 호환성
- 최신 모바일 브라우저(Chrome, Safari, Samsung Internet) 우선. iOS Safari / Android Chrome 우선 테스트.

### 10.6 접근성
- 핵심 액션 버튼 최소 44×44pt. 색상 대비 WCAG AA.

## 11. 범위 외 / 가정 / 미해결 이슈

### 11.1 가정 (검증되지 않았지만 전제로 두는 것)

- **A1.** 고수(중상급+)가 *블라인드 무대에서 실력 증명*을 원해 첫 챌린지에 제출한다 → 콜드 스타트 섭외로 검증.
- **A2.** 코인·뱃지·랭킹의 *사회적 인정*이 (현금화 없이도) 초기 동기로 작동한다 → 제출·재참여율로 검증.
- **A3.** 주 3챌린지(2일 주기)를 1인 운영자가 *지속 출제·검수·모니터링*할 수 있다 (AI 승인제·배치 비축 전제) → 운영 부담 모니터링. 안 되면 주기 환원.
- **A4.** 챌린지당 *제출자 5명*이 성립의 합리적 기준이다 → 실제 성립률로 검증.
- **A5.** 텍스트 결과물 + 저가 모델이면 월 $100 안에서 운영된다 → 예산 사용량 모니터링.
- **A6 (v1.1).** *AI 중립 요약이 투표 피로를 실제로 줄인다* + *요약이 사람 판단을 왜곡하지 않는다* → 투표 도달 분포·피드백으로 검증.

### 11.2 미해결 이슈 (개발 단계 또는 출시 후 결정)

- **I1.** Supabase Auth로 소셜(카카오/네이버)·이메일을 어디까지 통합 처리할지 — 셋업 시 확정.
- **I2.** 다중계정 편법 (계정 2개로 한쪽 제출·한쪽 정찰) — MVP 미대응. *편법 보상이 작음*(종료 후 전체 공개 + 블라인드 투표라 프롬프트를 안다고 표가 따라오지 않음). 악용 실제화 시 대응.
- **I3.** 시드(더미) 제출을 *예시로 표시할지* vs 자연스럽게 섞을지 — 신뢰 정체성과 직결, 관찰 후 결정.
- **I4.** 제출자가 제출 후 보는 투표가 *블라인드가 아닌* 점 — 순차 페이즈 모델에선 투표가 별도 기간에 열리므로 영향 작음. 표로 인정하되 데이터 관찰.
- **I5.** 자기표 허용이 순위에 주는 영향 — 전원 동일 조건이라 체계적 편향은 없으나 데이터 관찰.
- **I6.** 챌린지 성립 *제출자 5명*의 체감 적정선 — 운영자 + 베타 사용자 의견으로 조정.
- **I7.** 디자인 시안 — PRD 외 별도 단계.
- **I8 (v1.1).** AI 중립 요약이 *은근히 평가로 새는지*(앵커링 유발) 모니터링 — 새면 프롬프트 강화 또는 요약 축소/제거.
- **I9 (v1.1).** 1:1 비교 전환 트리거의 *구체 임계치*(출품작/투표자 비율) — 운영 데이터로 확정.
- **I10 (v1.3, 홀딩).** *신고 기능* — 요구 접수(이상한 결과물이 투표 무대에 노출됨). 방향은 정함: *사유 분류(부적절/부정행위/기타) + 로그인 사용자만 + 중복 신고 불가 + 자동삭제 없이 운영자 직접 판단 + 명백 위반은 투표 중 즉시·애매하면 종료 후.* **우선순위상 이번 사이클 미구현.** 다음 사이클 1순위 후보.
- **I11 (v1.3, 홀딩).** *제출 시 콘텐츠 사전 필터*(욕설·혐오·음란 자동 차단) — 신고(사후)와 함께 "두 겹 방어"로 권장되나 비용·구현 부담으로 홀딩. 신고와 같이 다음 사이클 검토.
- **I12 (v1.3).** 퀴즈 코인 보상 *구체 수치* — 운영하며 조정. 단 *마일스톤 상한* + *퀴즈 누적 < 챌린지 우승* 부등호는 고정.
- **I13 (v1.3).** 퀴즈 문항 *비축 소진* 시 운영 — 비축 잔량 모니터링. 공백일이 사용자 연승을 깨지 않도록 *출제된 날만 연승 카운트.*

### 11.3 특허(IP) 검토 메모 (운영 중 추가)

> 변리사 자문이 아니라 *방향 메모*. 실제 출원·가능성은 변리사 확인 필수.

- *플랫폼/서비스도 BM특허(영업방법 특허)로 출원 가능.* 단 "아이디어"가 아니라 *정보통신기술로 구체적으로 구현된 방법*이어야 함.
- **신규성 주의:** 이미 서비스가 *공개(론칭)*되었으므로 신규성 시계가 돌고 있을 수 있음. 공지예외 제도엔 *기간 제한*이 있어, *가능 여부와 데드라인을 변리사와 빠르게 확인*해야 함.
- 출원 후보가 될 만한 *기술적 메커니즘* 예: 페이즈 기반 베끼기 차단(제출 잠금→투표 개시→종료 시각 득표 스냅샷) + 투표 게이팅(3표 소진 시 프롬프트 열람 해제) + 블라인드 실행 파이프라인의 결합. (단 선행기술 조사 필요.)
- **전략 메모:** 초기엔 특허보다 *서비스 검증·성장*이 우선. 단 신규성 시계 때문에 *"상담만 빨리 받아 가능성·기한 확인"*해 두는 것이 균형점.

## 12. 운영 계획

### 12.1 출시 기준 (이미 소규모 운영 중 — 정식 확장 시 재확인)

| 항목 | 기준 |
|---|---|
| 콜드 스타트 | 첫 챌린지 *제출자 5명* 섭외 약속 확보 (본인 + 지인 + 부족분 시드) |
| 주제 비축 | AI 초안 받아 운영자가 다듬은 *검증된 주제 풀* 며칠치 |
| 실행 조건 확정 | Gemini *모델·온도·래퍼 텍스트* 고정값을 숫자로 확정 |
| 기능 | MVP 기능 전부 구현 및 베타 테스트 완료 |
| 법적 | 서비스 이용약관 + 개인정보 처리방침 게시 |
| 예산 | Gemini 월 상한 $100 + 80% 알림 설정, 챌린지 예산 게이트 동작 확인 |

### 12.2 가용 시간 및 일정

- **가용 시간:** 일 평균 약 6시간 (큰 자원).
  - 주의 1 — **범위 확대 유혹 경계.** 시간이 남으면 *Phase 2를 당기지 말고* MVP를 더 단단히/더 빨리 출시해 검증하는 데 쓴다.
  - 주의 2 — **출시 후 운영 노동 상존.** 주 2회 출제·검수·모니터링은 코딩이 끝나도 계속된다.
- **개발 가속:** Claude Code / Cursor.
  - 가속됨: 코드·보일러플레이트.
  - 가속 안 됨: 챌린지 출제·시드, 외부 디버깅(OAuth·Gemini), UX 결정, 운영.
- **기술 검증:** Gemini 서버 경유 호출 파이프라인은 *회사에서 사용 경험 있음* → 별도 spike 불필요.

### 12.3 위험 신호

- **주 2챌린지 운영이 버거움** → *7일 주기(주 1챌린지)로 즉시 완화.* (주기는 시각 설정값이라 변경 용이.)
- **(v1.2) 주 3챌린지(2일 주기) 출제·검수가 버거움** → 우선 *AI 승인제·배치 비축*이 작동하는지 점검. 그래도 버거우면 *3일 주기(주 2)로 즉시 환원*, 더 버거우면 7일 주기. *출제 부담 제거가 안 되면 주기 단축을 철회.*
- **순수 사용자 성립률이 계속 낮고 시드 의존도가 안 떨어짐** → 콜드 스타트 실패 신호. 섭외·홍보 재점검 또는 챌린지 빈도 축소.
- **예산 사용량이 예상보다 빠름** → 저가 모델 확인, 생성 한도/챌린지 빈도 조정.
- **범위가 부풀고 출시가 밀림** → Phase 2 항목을 다시 밀어내고 핵심만 출시.
- **(v1.1) 투표 피로가 안 풀리고 출품작이 투표자 수보다 과도** → 1:1 비교(4.6.3) 도입 검토.
- **(v1.1) AI 요약이 투표를 쏠리게 함(앵커링 징후)** → 요약 축소/톤 조정/제거.

### 12.4 기술 스택

- **호스팅:** Vercel
- **DB / Auth / Storage:** Supabase (Postgres / Auth / Storage)
- **AI 실행:** Gemini API (서버 경유 — Supabase Edge Function 등). 저가 모델 고정. 멀티 모델은 Phase 2. *요약 생성도 동일 경로.*
- **소셜 로그인:** 카카오/네이버 등 + 이메일 (Supabase Auth)

### 12.5 피드백 통로

- 앱 내 간단 문의 폼 (이메일 전송).

## 14. 부록

### 14.1 개발 시 챙길 핵심 메모

1. **서버 경유 Gemini 호출** — 키 노출 금지. 결과는 저장(재호출 방지). *요약 호출도 서버 경유.*
2. **모든 기간·한도 판정은 서버 시각·서버 데이터로.** 클라이언트 불신.
3. **챌린지 상태는 시각으로 계산** — `상태` 필드 직접 관리 금지.
4. **제출 = 확정 잠금** — 잠금 경고 모달 필수. *제출 시 요약 생성 트리거.*
5. **투표 중 득표·순위 숨김** — 종료 후 스냅샷 고정.
6. **예산: 챌린지 단위 게이트 + 콘솔 $100 상한 + 80% 알림 + 정직한 안내.** *게이트 계산에 (생성 3 + 요약 1) 반영.*
7. **카테고리·태그·고유 URL은 지금 심는다** (Phase 2 검색 씨앗, 소급 금지).
8. **로그인 후 원래 화면·행동으로 정확히 복귀.**
9. **(v1.1) 투표 화면 3종 세트:** 순서 랜덤화 + "전부 볼 필요 없음" 안내 + AI 중립 요약(접기 가능).
10. **(v1.1) AI 요약 프롬프트에 "평가 금지(색인만)" 명시** — 앵커링 차단. 실패 시 우아하게(요약 없이 표시).
11. **(v1.3) admin은 AI를 호출하지 않는다** — 챌린지·퀴즈 모두 *외부 AI 작성 → admin 등록만.* admin은 입력·관리 도구.
12. **(v1.3) 퀴즈 연승은 일별 기록 기반** — 하루 빠지면 초기화. 보상은 *매일 소액 + 마일스톤(상한)*, 그리고 *퀴즈 누적 < 챌린지 우승* 부등호 사수.
13. **(v1.3) 퀴즈는 작게 가둔다** — 리더보드·상점·카테고리로 부풀리지 말 것. 본체는 프롬프트 경진.

### 14.2 미래 수익 가설 (Phase 2 이후, 보관)

> 본질(학습·전체 공개·콘텐츠 누적)을 해치지 않는 선에서, 사람이 충분히 모인 뒤 재검토.

- 제출 횟수 추가 (무료 한도 넉넉히 + 초과분 유료) — 단 콘텐츠 생산 마찰 주의.
- 코인 현금화 / 우승 보상 (별풍선 → 현금화 경로).
- 검색 아카이브 위의 과금 (단 *학습 콘텐츠 자체는 무료 유지* 권장 — 지난 프롬프트 블라인드 과금은 학습 충돌로 신중).
- 기업용 사내 챌린지, 광고, 명예의 전당 등 *편의·확장·자아실현* 과금.

### 14.3 Phase 2 기능 후보 (보관)

- 검색 / 카테고리 탐색 페이지
- **1:1 비교(페어 투표) — 출품작 폭증 시 (트리거 4.6.3)**
- 사용자 주제 *제안* (운영자 검수 후 개최)
- 입력 변환형 / 멀티턴("3턴 내 최고 결과") 챌린지
- 병렬 2주제 동시 운영 (사람 안정 후)
- 이미지 생성 챌린지
- 멀티 모델 (GPT/Claude 등)
- 코인 사용처 / 코인 경제
- 출석 기반 뱃지
- 다크모드

### 14.4 용어 정리

- **MVP**: 최소 기능으로 출시해 학습하기 위한 버전.
- **운영자**: 이 서비스의 유일한 관리자. 챌린지 출제·시드·모니터링 담당.
- **챌린지(Challenge)**: 하나의 과제. 제출→투표→결과의 페이즈를 가짐.
- **생성 시도(Generation)**: 한 사용자가 한 챌린지에서 프롬프트를 실행한 한 번(최대 3회).
- **제출(Submission)**: 3회 생성 중 고른 1개. 확정 잠금.
- **블라인드 투표**: 결과물만 보고 투표. 프롬프트·작성자·득표는 가림.
- **시드 제출**: 콜드 스타트 방어를 위해 운영자가 채우는 출품작.
- **별풍선 통찰**: 보상의 1차 가치는 현금이 아니라 *사회적 인정의 가시화*라는 원리.
- **AI 중립 요약 (v1.1)**: 출품작 결과물의 *객관적 특징만* 묘사하는 색인. *평가·점수가 아님.* 투표 피로 완화용.
