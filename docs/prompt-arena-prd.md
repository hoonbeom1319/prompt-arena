# 프롬프트 아레나 (가칭) — PRD (Product Requirements Document)

> **버전:** v1.0 (MVP)
> **작성일:** 2026년 6월
> **상태:** 개발 착수 가능 (7단계 통과)

## 0. 이 문서를 읽는 법

이 문서는 1인 풀스택 개발자가 만드는 *AI 프롬프트 경진대회 서비스* MVP의 PRD입니다. 다음 원칙으로 작성되었습니다.

- **기능은 최소로, 구조는 확장 가능하게.** 모든 결정이 이 원칙을 통과했습니다.
- **결정에는 근거가 따라옵니다.** 6개월 뒤 *"왜 이렇게 정했지?"* 떠올릴 때 답을 주기 위해 근거를 같이 적었습니다.
- **빠진 것도 명시합니다.** Out of Scope와 Phase 2 섹션이 진짜 PRD의 절반입니다. 무엇을 *안 하는지*가 무엇을 하는지만큼 중요합니다.
- **이 서비스는 "행위의 기록"이 데이터의 본질입니다.** 장소·정보 같은 정적 데이터가 아니라 *생성했다·제출했다·투표했다*라는 시간 기반 행위가 중심이라, 시각(timestamp)과 상태 전이가 설계의 핵심입니다.

## 1. 배경과 문제 정의

### 1.1 배경

AI 프롬프트 엔지니어링이 현대인의 필수 역량이 되었지만, 두 가지가 어렵다.

1. **쓸 만한 프롬프트를 *찾기* 어렵다.** (탐색/큐레이션 문제)
2. **내가 짠 프롬프트가 잘 짠 것인지 *비교·검증·학습*하기 어렵다.** (평가 문제)

이 둘은 서로 다른 문제다. 경진대회+투표 포맷은 (2)를 직접 푸는 도구이고, (1)은 (2)로 쌓인 결과물이 누적되며 *부산물*로 따라온다.

### 1.2 핵심 문제

> 내가 짠 프롬프트가 잘 짠 것인지 *가늠할 기준*이 없다. 더 잘한 프롬프트가 뭐가 다른지 *비교·검증*할 무대가 없다.

같은 과제라도 누가 더 좋은 프롬프트를 짰는지 *공정하게 겨루고 검증*하는 장이 없다는 것이 본질이다.

### 1.3 서비스의 정체성

- **재미있는 3일 챌린지 + 투표를 엔진 삼아, 질 좋고 검증된 프롬프트를 카테고리별로 누적하는 서비스.**
- **장기 목적지:** "이런 상황엔 어떤 프롬프트?"를 검색해 *우승(검증된) 프롬프트*를 찾는 아카이브 + 그 위의 수익모델.
- **MVP의 일:** 그 아카이브의 *재료를 쌓는 엔진*(챌린지 + 투표)을 재미있게 작동시키는 것. **검색·수익화는 재료가 충분히 쌓인 Phase 2.**
- **닭이 먼저다.** 쌓인 게 없으면 검색할 것도 없다. 그래서 MVP는 *검색*이 아니라 *쌓는 엔진*이다.

## 2. 목표와 성공 지표

### 2.1 진짜 목표

> 질 좋고 검증된 프롬프트를 *지속적으로 누적*한다. 장기적으로 이 아카이브를 검색 서비스로 키우고 수익을 만든다.

수익은 (다)로 지향하지만, **MVP의 성공 지표로 삼지 않는다.** 대신 *"수익이 언젠가 얹힐 토대(사람이 모이고·머물고·다시 오는가)가 깔리는가"*를 본다.

### 2.2 측정 가능한 지표

**핵심 지표 (이 서비스가 본질을 하고 있는가)**

- **챌린지 성립률**: 한 챌린지가 *제출자 5명 이상*으로 마감되는 비율.
  - 목표 초안: *운영자 시드를 제외한 순수 사용자 제출만으로 70% 이상.*
  - 운영상 두 가지를 따로 본다: ① *시드 포함 성립률*(화면이 비지 않는가) ② *순수 사용자 성립률*(진짜 살아나는가).
  - 근거: 제출 5명이 안 되면 투표도 학습도 굶는다. 1순위 생존 지표.
- **제출 → 투표 전환**: 한 챌린지에서 제출 또는 투표한 활성 참여자 중 *투표 3표를 다 쓴* 비율.
  - 목표 초안: *50% 이상.*
  - 근거: 투표가 본질. 들어와 구경만 했는지 *실제로 참여했는지*를 본다.

**성장 지표 (서비스로 자라고 있는가)**

이 서비스는 3일 주기로 도니, *주 단위가 아니라 챌린지 단위*로 재방문을 본다.

- **챌린지 간 재참여율**: 이번 챌린지 참여자가 *다음 챌린지에도* 참여하는 비율. 목표 초안: *30% 이상.*
- **신규 → 2회차 잔존**: 처음 참여한 사람이 *두 번째 챌린지*까지 오는 비율.

**건강 지표 (토대가 멀쩡한가)**

- **운영자 시드 의존도**: 전체 제출 중 운영자 시드가 차지하는 비율. *낮아질수록 성공.* (안 떨어지면 "사람이 안 모인다"는 위험 신호 → 13장 연결)
- **AI 주제 적격률**: AI 초안 챌린지 주제 중 운영자가 *수정 없이 통과*시킨 비율. (낮으면 출제 AI 프롬프트 개선 필요, 운영 부담 직결)

**측정 까다로운 것 (지표 후보로만 보관)**

- **학습이 일어났는가**: 직접 측정 불가. *재참여자의 제출이 이전보다 더 많은 표를 받는가*(실력 향상의 대리지표)를 데이터가 쌓이면 관찰.

### 2.3 지표 운영 원칙

- 위 숫자는 *기준선*이지 정답이 아니다. 운영하며 조정.
- 측정 불가능한 목표("실력을 키운다")가 아니라 *행동의 흔적*으로 환산한다.

## 3. 타깃 사용자

### 3.1 핵심 통찰 — 제출자(생산자)는 항상 소수다

거의 모든 경진/UGC 서비스에서 *콘텐츠를 생산하는 사람*은 소수(보통 1:9~1:99)다. 따라서 **"제출자(고수)를 어떻게 확보하느냐"가 서비스 생사의 9할**이다. 투표자는 상대적으로 모으기 쉽다. *생산자가 귀하다.*

### 3.2 핵심 사용자

**1번 사용자 (MVP 핵심 = 제출자): AI를 실무·취미로 자주 쓰는 중상급~고수**

- 프롬프트에 자기 나름의 노하우와 자부심이 있고, *그게 통하는지 검증받고 싶은* 사람.
- **동기:** 익명·블라인드 무대에서 *순수 실력으로 1등을 증명*하고, 그 증명을 코인·뱃지·랭킹이라는 *눈에 보이는 숫자로 박제*하는 것.
- 근거:
  1. **콜드 스타트는 콘텐츠 품질로 깬다.** 텅 빈 서비스에 감탄할 프롬프트가 있어야 사람이 남는다. 초기엔 양보다 질이 사람을 붙잡고, 그 질의 원천은 고수다.
  2. **메인 목표가 "질 좋고 검증된 프롬프트 누적"** — 그 질의 원천이 고수다.
  3. **이탈 방지.** 입문자를 타깃으로 잡으면 매번 깨져서 상처받고 떠난다. 고수는 *이기려고* 남고, 입문자는 *구경·학습*하러 부담 없이 온다.

**2번 사용자 (동시 존재, 화면 우선순위 낮음 = 투표자): AI에 관심 있는 입문~중급자**

- 직접 내긴 부담스럽지만 *구경하고 투표하며 배우고 싶은* 사람.
- 제출자의 콘텐츠에 *끌려와* 투표자로 참여, 코인을 모으고, 일부는 나중에 제출자로 자란다.

### 3.3 "별풍선" 통찰 — 코인·뱃지·랭킹의 1차 가치

초기 고수가 텅 빈 서비스에 첫 프롬프트를 내는 동기는 *코인/상금*이 아니다(쓸 데도 자랑할 사람도 없으므로). 진짜 동기는 **"내 프롬프트가 남들 것보다 낫다는 걸 *눈에 보이는 표로* 증명받고 싶다"**는 **사회적 인정 욕구**다.

> 코인·뱃지·랭킹의 1차 가치는 "현금화"가 아니라 **"실력이 숫자로 증명되는 사회적 인정의 가시화"**다. 현금화(수익)는 나중에 얹는 두 번째 동력이다.

출력 블라인드 투표(결과물만으로 평가)는 이 욕구를 정확히 채운다 — 순수하게 결과로 1등을 먹으면 그건 *운이나 인맥이 아닌 실력의 증명*이다.

### 3.4 재미의 정의

- **(가) 경쟁·랭킹의 재미** (내가 몇 등인가) + **(다) 성취의 재미** (코인·뱃지·우승).
- **(나) 발견의 재미** (남의 기발한 프롬프트 구경)는 Phase 2 검색 아카이브와 함께 자연히 따라온다.

### 3.5 콜드 스타트 (빈집 문제) 대응

- **출시 전 제출자 확보:** 첫 챌린지 성립(*제출자 5명*)을 위해, *구체적으로 섭외 약속을 받은 사람*을 미리 확보 (본인 + AI 잘하는 지인 직접 섭외 + 부족분 운영자 시드). 막연한 "퍼지겠지"가 아니라 *손에 잡히는 개별 섭외.*
- **서비스 내 신원 표시:** *전원 익명/닉네임.* 출력 블라인드 평가 정신과 일관. (운영자의 비공개 섭외 명단과 서비스 표시는 다른 층위.)
- **홍보(투표자·확산):** MVP에선 *지인·관련 커뮤니티(개발자 채널, AI 오픈채팅 등) 직접 알리기* 수준으로 최소화. 본격 확산은 콘텐츠가 쌓이는 Phase 2의 일.

## 4. 기능 요구사항

### 4.0 핵심 메커니즘 (모든 기능이 매달린 척추)

**A. 제출 메커니즘**
- 한 사용자는 한 챌린지에서 프롬프트를 *최대 5회 생성·시도*할 수 있다(각 시도 = Gemini 1회 실행).
- 5개 중 *1개를 선택해 제출*한다.
- **제출은 확정 잠금** (수정·삭제 불가).

**B. 실행의 공정성**
- 모든 제출의 결과물은 **시스템이 Gemini API로 동일 조건(모델·온도·래퍼 텍스트 고정)으로 실행**한다.
- 실행 조건이 다르면 투표가 *실력*이 아니라 *운 좋은 출력*을 평가하게 되므로, 조건 고정은 타협 불가.

**C. 순차 진행 (페이즈 모델) — 제출과 투표는 시간으로 분리된다**
- 제출 기간엔 투표가 닫혀 있고, 투표 기간엔 제출이 마감된다.
- 이 페이즈 분리가 **베끼기를 원천 차단**한다(제출 중엔 아무도 못 보고, 투표 중엔 봐도 더 못 낸다). 따라서 *개인별 잠금 규칙은 불필요* — 페이즈가 자동 해결.

**D. 출력 블라인드 투표**
- 투표 기간엔 *결과물만* 보인다. 프롬프트 본문과 작성자는 가려진다.
- *투표 중 득표수·순위는 숨긴다* (밴드왜건/쏠림 방지). 종료 후 공개.

**E. 프롬프트 공개(학습 재료 해제) 규칙**
- 투표 3표를 다 쓰면 → 그 챌린지의 *전체 프롬프트 열람 해제* (나).
- 챌린지 종료 시 → *전체 공개* (다).
- 미제출 생성 시도는 *본인만* 열람(타인에게 절대 비공개).

**F. 투표**
- 챌린지당 *최대 3표.*
- *자기 출품작에도 투표 가능* (단, 3표 한도에 포함 — 보너스표 아님. 전원에게 동일하게 열려 있어 체계적 편향 없음).

### 4.1 MVP 포함 기능

| # | 기능 | 우선순위 | 근거 ("없으면 어떻게 되나") |
|---|---|---|---|
| 1 | 챌린지 조회 (진행 중 / 상태별) | 핵심 | 서비스의 입구. 없으면 아무것도 시작 안 됨 |
| 2 | 프롬프트 생성·시도 (Gemini 실행, 5회 한도) | 핵심 | 제출의 전제. 결과물이 여기서 나옴. 비용이 나가는 화면 |
| 3 | 출품작 제출 (5회 중 1개 선택, 확정 잠금) | 핵심 | 콘텐츠 생산의 핵심 행동 |
| 4 | 투표 (3표 한도, 자기표 허용·한도 포함) | 핵심 | *본질.* 없으면 검증이 안 됨 |
| 5 | 프롬프트 열람 게이팅 (투표 3표→전체 / 종료→전체) | 핵심 | 학습 재료 공개 규칙. 본질과 직결 |
| 6 | 챌린지 상태 전이 (제출→투표→결과, 시각 기반) | 핵심 | 순차 모델의 척추. 없으면 일정이 안 돎 |
| 7 | 결과·순위 공개 (종료 후) | 핵심 | 경쟁의 보상. (가) 재미의 핵심 |
| 8 | 인증 (소셜 + 이메일 로그인) | 핵심 | 5회·3표 한도·코인은 *사용자 식별* 필수 |
| 9 | 코인 적립·잔액 (우승 + 활동) | 중요 | (다) 재미·동기 엔진. *적립만*, 사용처는 Phase 2 |
| 10 | 뱃지·랭킹 | 중요 | (가)(다) 재미. "실력의 가시화"(별풍선 통찰) |
| 11 | 카테고리·태그 부착 | 중요 | Phase 2 검색의 씨앗. *지금 안 심으면 소급 지옥* |
| 12 | 우승 프롬프트 고유 URL·공유 | 보조 | 아카이브 씨앗 + 자연 확산 |
| 13 | 관리자: 챌린지 출제 (AI 초안 → 운영자 확정) | 핵심 | 주제 공급 = 서비스 연료 |
| 14 | 관리자: 시드 제출 (콜드 스타트) | 핵심 | 초기 빈집 방어 1차선 |
| 15 | 관리자: 결과·출품작 모니터링·사용자/코인 관리 | 핵심 | 운영의 본진 |

### 4.2 MVP 제외 — 다음 버전 (Phase 2)

| 기능 | 사유 |
|---|---|
| 검색 / 카테고리 탐색 페이지 | 쌓인 게 없으면 빈 검색창. 씨앗(카테고리·태그·고유 URL)만 MVP에 심음 |
| 사용자 주제 *제안* (운영자 검수 후 개최) | 좋은 성장 장치지만, 사용자 모인 뒤 가치. 초기엔 주제 부족 없음 |
| 입력 변환형 챌린지 (고정 입력을 가공) | 데이터·실행 복잡. 단독 생성형으로 충분 |
| 멀티턴 챌린지 ("3턴 내 최고 결과") | 고도화 형태. 챌린지 유형 필드로 확장 여지만 둠 |
| 병렬 2주제 동시 운영(고르기) | 제출자·투표자를 둘로 쪼개 콜드 스타트 악화. 사람 안정되면 개방 |
| 이미지 생성 챌린지 | 비용·저장·평가 난이도↑. 텍스트로 시작 |
| 멀티 모델 (GPT/Claude 등) | Gemini 단일로 시작. "돈 벌면" 확장 |
| 실제 결제·현금화 | 설계만(데이터 모델 열어둠). 진짜 결제는 Phase 2 |
| 코인 사용처 / 코인 경제 | 적립만 MVP. 사용처 열면 밸런싱 늪 → 1인 운영 위험 |
| 출석 기반 뱃지 | 3일 주기와 안 맞음. "연속 참여" 류로 대체 가능 |
| 실시간 순위 표시 | 블라인드 투표를 깸 (밴드왜건). 종료 후 공개 |
| 댓글·팔로우·DM·자유서술 후기 | 본질 아님 |
| 정보 제보(부정 신고) 화면 | 초기엔 운영자 직접 모니터링·삭제로 갈음 |

### 4.3 명시적 Out of Scope (영구 제외 또는 정체성 충돌)

| 항목 | 사유 |
|---|---|
| **사용자가 직접 챌린지 *개최*** (검수 없는 즉시 게시) | 잡다·미검증·빈집 양산. "질 좋고 검증된" 정체성과 충돌. *제안*(운영자 검수)으로 대체 |
| 클라이언트(브라우저) 시간 신뢰 | 보안 위반. 모든 판정은 서버 시각으로 |

### 4.4 기능 명세 (상세 동작)

#### F-1. 챌린지 조회 / 첫 화면
- 첫 화면 = **지금 진행 중인 챌린지 하나**를 크게 보여준다 (목록형 아님).
  - 근거: 본질이 "지금 이 챌린지에 참여하라". 고르게 하면 에너지 낭비 + 초기엔 고를 것도 없음.
- 첫 화면은 **현재 서버 시각 기준 상태에 따라 4개 뷰로 분기**한다(아래 F-2).
- 목록·지난 챌린지는 *부가 동선*(별도 화면).

#### F-2. 첫 화면 — 상태별 4뷰 분기

| 들어온 시점 | 보여주는 것 | 핵심 행동 |
|---|---|---|
| **제출 기간** | 주제 + 참가자 수 + 마감 카운트다운 + *내 제출 상태* | [프롬프트 만들기] / [내 제출 보기] |
| **투표 기간** | 주제 + 출품작 리스트(결과물만, 블라인드) + *내 투표 상태(N/3)* | [투표하러 가기] |
| **결과 기간 / 종료 후** | 주제 + 최종 순위 + 우승작 + *전체 프롬프트 공개* | [결과 보기] |
| **공백(일요일 등)** | 진행 중 챌린지 없음 → 지난 결과로 안내 | [지난 결과 보기] |

- **로그인/비회원 분기:** 비회원은 주제·출품작·결과 *구경 가능*. 단 [만들기]·[제출]·[투표]를 누르면 *로그인 유도.* 로그인 사용자에게만 *"내 상태"*가 얹힌다.
- **제출 기간 화면 비어 보임 방지:** 타인 출품작·프롬프트는 비공개로 막되, *주제·참가자 수·남은 시간·내 상태*로 채운다. (표현 디테일 — 스켈레톤/카운터 등 — 은 디자인 단계, 9장 참고.)

#### F-3. 프롬프트 생성 화면 (가장 공들여야 하고 돈이 나가는 화면)
- 구성: *주제 표시 + 프롬프트 입력 + [실행] + 결과물 표시 + 남은 횟수(N/5) + 재시도 + 제출 선택.*
- 사용자가 프롬프트 입력 → [실행] → 시스템이 *서버 경유*로 Gemini 호출 → 결과물 표시 (1회차).
- 마음에 안 들면 다시 입력·실행 (최대 5회). **5회 소진 시 생성 잠금.**
- **5회 한도는 서버가 카운트해 막는다** (API 비용 방어선).
- **실행 실패(API 에러) 시 횟수 차감하지 않음** (사용자 잘못 아님 + 항의 CS 방지). *성공했으나 결과가 불만족인 경우는 차감.*
- 엣지: 예산 한도 도달 시 — 4.0/10장/13장의 예산 정책에 따라 *정직한 안내* ("선착순 마감" 등 오해 문구 금지).

#### F-4. 제출 확정
- 5개 생성 시도 중 1개 선택 → [제출].
- **확정 경고 모달**: *"제출하면 수정·삭제할 수 없어요. 계속할까요?"* → 확인 시 잠금.
- 제출 후 첫 화면은 "제출 완료" 상태로.
- 한 사용자는 한 챌린지에 *최대 1개 제출.*

#### F-5. 투표 (투표 기간)
- 출품작 리스트 = *결과물만* 표시 (프롬프트·작성자 가림).
- 출품작 탭 → 상세에서 결과물 정독 → [이 작품에 투표] → 1표 소진.
- 최대 3표. *자기 출품작에도 투표 가능*(3표에 포함).
- **3표를 다 쓰면 → 그 챌린지 전체 프롬프트 열람 해제** (나). 이후 각 출품작의 프롬프트까지 보며 학습.
- *투표 중 득표·순위 숨김.*
- 서버는 매 투표 요청 시 *서버 시각으로* "투표 기간인가 + 3표 미만인가"를 재판정.

#### F-6. 결과·순위 (결과 기간 / 종료 후)
- 최종 순위 + 우승작 + *전체 프롬프트 공개* (다).
- 우승작 상세 → 결과물 + 프롬프트 전체 → 학습.
- 우승 프롬프트 [공유] → *고유 URL 복사* (아카이브 씨앗 + 확산).
- 제출자는 *내 순위·득표·획득 코인* 확인.
- 종료 시점에 득표를 집계해 *Submission에 최종 득표·순위를 스냅샷으로 고정*하고 코인을 지급한다.

#### F-7. 인증 (로그인)
- **소셜 로그인 + 이메일 로그인** (Supabase Auth 통합).
- *이메일 가입 시 인증 메일 확인*을 거친다 (다중계정·봇 일부 방지).
- 생성·제출·투표는 *로그인 필수.* 비회원은 구경만.
- 행동 시도 시 로그인 게이트 → 로그인 후 *원래 보던 화면·행동으로 복귀.*

#### F-8. 코인 (적립 전용)
- *우승*과 *활동(제출·투표 등)*으로 적립. 신규도 활동으로 모을 수 있어 부익부 완화.
- **MVP는 적립만.** 사용처 없음(Phase 2). *명성·랭킹 점수*로 표시.
- 모든 적립은 원장(CoinTransaction)에 기록.

#### F-9. 뱃지·랭킹
- **MVP 뱃지(전부 기존 기록으로 산출 가능):** 첫 제출 / 첫 우승 / 우승 N회 / 투표 N회 / (선택) 챌린지 연속 참여 N회.
- *일회성*(첫 제출·첫 우승)과 *누적형*(N회)으로 구분. 누적형은 Submission·Vote 기록에서 카운트.
- **출석 기반 뱃지는 Phase 2** (3일 주기와 안 맞음. 일별 방문 기록도 현재 모델에 없음).
- 랭킹: 코인·우승 횟수 등으로 산출 (구체 산식은 운영하며 조정).

#### F-10. 카테고리·태그 (Phase 2 씨앗)
- 챌린지에 *카테고리* 1개를 부착(드롭다운). 필요 시 태그.
- MVP에선 *검색·탐색 기능 없음.* 단 모든 챌린지에 메타데이터를 *처음부터* 달아둔다 (나중에 소급 태깅은 지옥).

#### F-11. 링크 공유
- 결과·우승 프롬프트 화면에서 공유 → *고유 URL 클립보드 복사.*
- 받은 사람이 *앱 설치 없이 웹*에서 바로 진입.

### 4.5 일정·페이즈 명세 (서비스의 시계)

```
월 00:00 ~ 23:59  제출 (주제 공개 + 생성·제출)
화 00:00 ~ 23:59  투표 (출품작 공개, 블라인드 투표)
수 00:00 ~ 23:59  결과 (순위·우승·전체 프롬프트 공개, 코인 지급) + 목요일 챌린지 주제 예고
목 00:00 ~ 23:59  제출
금 00:00 ~ 23:59  투표
토 00:00 ~ 23:59  결과 + 다음 주 월요일 챌린지 주제 예고
일               휴식 (새 챌린지 없음, 지난 결과 열람만)
```

- **주기:** 3일 주기, 주 2챌린지 (월~수, 목~토).
- **주제 예고:** *각 결과일에 직전 예고* (방식 1). 수요일에 목요일 주제, 토요일에 다음 주 월요일 주제. 일요일은 순수 휴식. → "결과 보는 날 = 다음 주제 나오는 날" 규칙으로 인지·운영 단순.
- **비상 탈출구:** 주 2챌린지 운영이 버거우면 *7일 주기(주 1챌린지: 제출3·투표3·결과/예고1)*로 즉시 완화. 주기는 시각 설정값이라 변경 용이. (13장 위험 신호 연결.)

## 5. 관리자 페이지 요구사항

### A-1. 관리자 인증
- 사용자 인증(소셜/이메일) 재사용 + User의 *관리자 여부* 속성으로 권한 식별.

### A-2. 대시보드
- 진행 중/예정 챌린지 상태, 새 출품 현황, 예산 사용량(월 $100 대비), 빠른 진입 [챌린지 출제] [시드 제출].

### A-3. 챌린지 출제 (AI 초안 → 운영자 확정)
- *AI 초안 생성*(챗봇 형태로 주제 후보 제안) → 운영자가 *검토·수정·확정.*
- 입력 필드: 주제(제목 + 지시문), 카테고리(드롭다운), 챌린지 유형(MVP: 단독생성형 고정), 제출/투표/결과 시각, 실행 조건(모델·온도 — 기본값 자동 채움), 예고 시각.
- 출제 시 *예산 게이트* 통과 확인 (A-7 참고).
- 채점 가능한(우열이 갈리는) 주제인지 운영자가 최종 판단. — 큐레이션 = 손맛.

### A-4. 시드 제출 (콜드 스타트)
- 운영자가 챌린지에 *시드 출품작*을 직접 추가해 빈집 방어.
- *시드를 예시로 표시할지 / 자연스럽게 섞을지*는 미해결 이슈(12장)로 관찰.

### A-5. 출품작·결과 모니터링
- 진행 중·종료 챌린지의 출품작(결과물) 목록 조회.
- 부정 출품(욕설·도배 등) *직접 삭제* (별도 제보 화면 없이 운영자 모니터링으로 갈음).
- 종료 후 순위·득표 확인.

### A-6. 사용자·코인 관리
- 사용자 목록, 닉네임/상태, 코인 잔액·적립 내역 조회.
- 필요 시 수동 조정(예외 대응).

### A-7. 예산 관리
- 월 예산 상한 $100 대비 *현재 사용량* 표시. 80% 도달 시 *운영자 알림.*
- *새 챌린지 열기 전 예산 게이트*: 남은 예산이 한 챌린지 풀(예: 최대 제출자 수 × 5회) 이상인지 확인. 부족 시 신규 챌린지 보류.

```
  - 누가 (User 참조)

  - 어느 생성시도를 제출했나 (Generation 참조)
  - 제출 시각
  - 확정 잠금 (수정·삭제 불가)
  - 최종 득표수 (종료 후 스냅샷)
  - 최종 순위 (종료 후 스냅샷)
  ※ 한 User는 한 Challenge에 최대 1개

[투표 Vote]                    ← 본질, "3표 한도"의 실체
  - 투표 ID
  - 누가 (User 참조)
  - 어느 챌린지 (Challenge 참조)
  - 어느 제출에 (Submission 참조)
  - 투표 시각
  ※ 한 User는 한 Challenge에 최대 3개
  ※ 자기 Submission에도 투표 가능(3표 한도에 포함)

[코인거래 CoinTransaction]      ← 잔액의 근거(원장). MVP는 적립만
  - 거래 ID
  - 누가 (User 참조)
  - 변동량 (+; 사용처는 Phase 2이므로 MVP는 +만)
  - 사유 (우승 / 활동보상-제출 / 활동보상-투표 등)
  - 관련 챌린지 (선택, Challenge 참조)
  - 거래 시각

[뱃지 Badge]
  - 뱃지 ID / 이름 / 조건 설명 / 아이콘
[사용자뱃지 UserBadge]
  - (연결) 누가 / 어느 뱃지 / 획득 시각
```

### 6.2 관계 한눈에

```
Category   1 ─ N  Challenge
Challenge  1 ─ N  Generation
Challenge  1 ─ N  Submission
Challenge  1 ─ N  Vote
User       1 ─ N  Generation     (한 챌린지당 최대 5)
User       1 ─ N  Submission     (한 챌린지당 최대 1)
User       1 ─ N  Vote           (한 챌린지당 최대 3)
Submission 1 ─ N  Vote           (한 제출이 여러 표를 받음)
Generation 1 ─ 1  Submission     (제출은 생성시도 하나를 가리킴)
User       1 ─ N  CoinTransaction
User       N ─ M  Badge          (UserBadge 중간)
```

### 6.3 설계 원칙

- **챌린지 상태는 저장값이 아니라 시각으로 계산한다.** `상태` 필드를 직접 저장·관리하면 1인 운영자가 제때 못 바꿔 데이터가 거짓말을 한다. *4개 시각만 저장하고 현재 서버 시각과 비교*해 제출중/투표중/결과를 매번 계산하면 시간이 흐르며 자동 전이된다. (`상태` 필드를 둔다면 캐시용으로만.)
- **시각의 진실은 항상 서버.** 모든 제출·투표 요청은 *서버가 자기 시각으로* 기간·한도를 재판정해 허용/거부. 클라이언트 시간은 *카운트다운 표시용*으로만(서버 시각 동기화). 사용자가 브라우저 시간을 바꿔도 판정에 영향 없음.
- **득표수는 투표 중엔 Vote에서 계산(숨김), 종료 후 Submission에 스냅샷 고정.** 진실의 원천은 Vote 기록.
- **생성 시도 전부 저장 + 미제출은 본인만 열람.** 장기적으로 *프롬프트 개선 과정* 데이터 자산이 됨. 미제출 비공개는 베끼기 방지와도 일치. (저장 비용은 텍스트 한정으로 억제.)
- **코인은 적립 전용(MVP).** 사용처를 안 만들어 *화폐 밸런싱 늪*을 회피. 데이터 모델은 사용(-)도 가능하게 열어두되 MVP에선 +만.
- **닉네임은 UUID 식별 + 중복 허용 + 표시 꼬리표.** 유니크 강제 없이 가입이 막히지 않으면서, 표시 시 동명이인 혼동을 식별자 꼬리표로 해소.

## 7. 사용자 흐름

### 7.1 시나리오 ① — 제출자(고수)의 제출일

```
앱 열기 → [첫 화면: 제출 기간 뷰] 주제 확인
  → [프롬프트 만들기] (비회원이면 로그인)
  → 프롬프트 입력 → Gemini 실행 → 결과물 확인  (1회차)
  → 불만족 → 다시 입력·실행  (2~5회차, 5회 소진 시 잠금)
  → 5개 중 1개 선택 → [제출] → 확정 경고("수정·삭제 불가") → 잠금
  → [첫 화면] "제출 완료" 상태로 복귀
```

### 7.2 시나리오 ② — 투표자의 투표일

```
앱 열기 → [첫 화면: 투표 기간 뷰] 출품작 리스트(결과물만)
  → 출품작 탭 → [출품작 상세] 결과물 정독 (프롬프트 가림)
  → [이 작품에 투표] (비회원이면 로그인) → 1표 소진
  → 리스트로 돌아가 비교, 최대 3표
  → 3표 다 쓰면 → 그 챌린지 전체 프롬프트 열람 해제(나)
  → 각 출품작 프롬프트까지 보며 학습
```

### 7.3 시나리오 ③ — 종료 후 결과·학습

```
결과 기간 진입 → [첫 화면: 결과 뷰] 최종 순위 + 우승작
  → 우승작 탭 → [출품작 상세] 결과물 + 프롬프트 전체 공개
  → "이 프롬프트가 왜 1등인지" 학습
  → 우승 프롬프트 [공유] → 고유 URL 복사
  → (제출자라면) 내 순위·득표·획득 코인 확인
```

### 7.4 로그인 후 복귀 흐름

```
비회원이 [만들기]/[제출]/[투표] 시도
  → [로그인 게이트] 소셜/이메일
  → (이메일이면 인증 메일 확인)
  → 콜백 후 *원래 보던 화면·행동으로 복귀*
```

## 9. 디자인 방향

### 9.1 톤

- **경쟁의 긴장감 + 신뢰감.** 실력을 겨루는 무대이므로 *집중되고 또렷한* 톤. 동시에 *공정성·투명성*이 느껴지게(블라인드·정직한 안내).
- **성취의 가시화.** 코인·뱃지·랭킹·순위가 *눈에 보이는 보상*으로 또렷하게 드러나야 함 (별풍선 통찰).

### 9.2 화면별 디자인 메모

- **제출 기간 화면이 비어 보이지 않게**: 참가자 카운터, 남은 시간, 스켈레톤 등 *기대감·긴장감을 주는 장치* 검토. (규칙은 "타인 출품작 비공개", 표현은 디자인 단계에서.)
- **생성 화면**: 남은 횟수(N/5), 실행 로딩, 결과물, 재시도, 제출 선택이 한 흐름으로. 5회가 *소중하게* 느껴지도록.
- **투표 화면**: 블라인드(결과물만) 강조. 득표·순위는 *숨김*이 디자인으로도 분명히.

### 9.3 디바이스 우선순위

- **모바일 웹 우선.** 데스크톱은 관리자 페이지 위주(반응형 가능 범위까지).

### 9.4 다크모드

- **MVP 미지원.** 출시 후 요청 모이면 검토.

## 10. 비기능 요구사항

### 10.1 성능
- 첫 화면 로딩: 모바일 환경에서 빠른 첫 콘텐츠 표시.
- *생성(Gemini 실행)*은 비동기 — 로딩 상태를 명확히 표시(수 초 소요 가능).

### 10.2 보안 / 프라이버시 (이 서비스의 핵심 비기능)
- **Gemini API는 반드시 *서버 경유*로 호출** (Supabase Edge Function 등). 프론트 직접 호출 금지 — API 키 노출 차단.
- **모든 기간·한도 판정은 서버 시각·서버 데이터로.** 클라이언트 시간/입력 불신.
- 사용자 데이터 최소 수집 (인증 식별자 + 닉네임 + 활동 기록).
- 이메일 가입 시 *인증 메일 확인.*
- 약관·개인정보 처리방침 *출시 전 게시 필수.*

### 10.3 비용 방어 (Gemini 예산)
- **키 1개 + 우리 서비스가 호출 수를 카운트해 통제** (Generation 기록으로 산출).
- **챌린지 단위 예산 게이트:** 새 챌린지 열기 전 *남은 월 예산 ≥ 한 챌린지 풀(최대 제출자 수 × 5회)* 확인. 부족 시 신규 챌린지 보류 — *진행 중 챌린지는 영향 없음(시작한 경기는 끝까지 보장).*
- **콘솔 월 상한 $100 + 80% 도달 시 운영자 알림** — 코드 통제가 뚫려도 막는 *최후 안전망.*
- **저가 모델(Flash 계열) 고정**으로 단가 억제.
- **그럼에도 한도 도달 시: 사용자에게 *정직한 안내*** ("선착순 마감" 등 오해 문구 금지. 예: "지금은 생성 요청이 많아 잠시 어려워요. 다음 챌린지에서 만나요.").
- 정교한 호출별 예약(reservation)은 *Phase 2 최적화.* MVP는 챌린지 단위 게이트로 시작.

### 10.4 데이터 무결성
- 제출은 *확정 잠금* (수정·삭제 불가).
- 동네/카테고리/실행조건 등은 *미리 정한 목록·고정값*에서 선택.
- 시드 반영·관리자 조정 등 데이터 변경은 운영자 확인 절차.

### 10.5 호환성
- 최신 모바일 브라우저(Chrome, Safari, Samsung Internet) 우선. iOS Safari / Android Chrome 우선 테스트.

### 10.6 접근성
- 핵심 액션 버튼 최소 44×44pt. 색상 대비 WCAG AA.

## 11. 범위 외 / 가정 / 미해결 이슈

### 11.1 가정 (검증되지 않았지만 전제로 두는 것)

- **A1.** 고수(중상급+)가 *블라인드 무대에서 실력 증명*을 원해 첫 챌린지에 제출한다 → 콜드 스타트 섭외로 검증.
- **A2.** 코인·뱃지·랭킹의 *사회적 인정*이 (현금화 없이도) 초기 동기로 작동한다 → 제출·재참여율로 검증.
- **A3.** 주 2챌린지를 1인 운영자가 *지속 출제·검수·모니터링*할 수 있다 → 운영 부담 모니터링.
- **A4.** 챌린지당 *제출자 5명*이 성립의 합리적 기준이다 → 실제 성립률로 검증.
- **A5.** 텍스트 결과물 + 저가 모델이면 월 $100 안에서 운영된다 → 예산 사용량 모니터링.

### 11.2 미해결 이슈 (개발 단계 또는 출시 후 결정)

- **I1.** Supabase Auth로 소셜(카카오/네이버)·이메일을 어디까지 통합 처리할지 — 셋업 시 확정.
- **I2.** 다중계정 편법 (계정 2개로 한쪽 제출·한쪽 정찰) — MVP 미대응. *편법 보상이 작음*(종료 후 전체 공개 + 블라인드 투표라 프롬프트를 안다고 표가 따라오지 않음). 악용 실제화 시 대응.
- **I3.** 시드(더미) 제출을 *예시로 표시할지* vs 자연스럽게 섞을지 — 신뢰 정체성과 직결, 관찰 후 결정.
- **I4.** 제출자가 제출 후 보는 투표가 *블라인드가 아닌* 점 (제출 즉시 열람 가능 시) — 단, 순차 페이즈 모델에선 투표가 수요일에 열리므로 이 이슈의 영향은 작음. 표로 인정하되 데이터 관찰.
- **I5.** 자기표 허용이 순위에 주는 영향 — 전원 동일 조건이라 체계적 편향은 없으나 데이터 관찰.
- **I6.** 챌린지 성립 *제출자 5명*의 체감 적정선 — 운영자 + 베타 사용자 의견으로 조정.
- **I7.** 디자인 시안 — PRD 외 별도 단계.

### 12.2 가용 시간 및 일정

- **가용 시간:** 일 평균 약 6시간 (큰 자원).
  - 주의 1 — **범위 확대 유혹 경계.** 시간이 남으면 *Phase 2를 당기지 말고* MVP를 더 단단히/더 빨리 출시해 검증하는 데 쓴다.
  - 주의 2 — **출시 후 운영 노동 상존.** 주 2회 출제·검수·모니터링은 코딩이 끝나도 계속된다.
- **개발 가속:** Claude Code / Cursor.
  - 가속됨: 코드·보일러플레이트.
  - 가속 안 됨: 챌린지 출제·시드, 외부 디버깅(OAuth·Gemini), UX 결정, 운영.
- **기술 검증:** Gemini 서버 경유 호출 파이프라인은 *회사에서 사용 경험 있음* → 별도 spike 불필요.
- **출시 목표:** 약 3개월 내 (단, *데이터/섭외 준비가 코드보다 느릴 수 있음*).

### 12.3 위험 신호

- **주 2챌린지 운영이 버거움** → *7일 주기(주 1챌린지)로 즉시 완화.* (주기는 시각 설정값이라 변경 용이.)
- **순수 사용자 성립률이 계속 낮고 시드 의존도가 안 떨어짐** → 콜드 스타트 실패 신호. 섭외·홍보 재점검 또는 챌린지 빈도 축소.
- **예산 사용량이 예상보다 빠름** → 저가 모델 확인, 생성 한도/챌린지 빈도 조정.
- **범위가 부풀고 출시가 밀림** → Phase 2 항목을 다시 밀어내고 핵심만 출시.

### 12.4 기술 스택

- **호스팅:** Vercel
- **DB / Auth / Storage:** Supabase (Postgres / Auth / Storage)
- **AI 실행:** Gemini API (서버 경유 — Supabase Edge Function 등). 저가 모델 고정. 멀티 모델은 Phase 2.
- **소셜 로그인:** 카카오/네이버 등 + 이메일 (Supabase Auth)

### 12.5 피드백 통로

- 앱 내 간단 문의 폼 (이메일 전송).

## 14. 부록

### 14.1 개발 시 챙길 핵심 메모

1. **서버 경유 Gemini 호출** — 키 노출 금지. 결과는 저장(재호출 방지).
2. **모든 기간·한도 판정은 서버 시각·서버 데이터로.** 클라이언트 불신.
3. **챌린지 상태는 시각으로 계산** — `상태` 필드 직접 관리 금지.
4. **제출 = 확정 잠금** — 잠금 경고 모달 필수.
5. **투표 중 득표·순위 숨김** — 종료 후 스냅샷 고정.
6. **예산: 챌린지 단위 게이트 + 콘솔 $100 상한 + 80% 알림 + 정직한 안내.**
7. **카테고리·태그·고유 URL은 지금 심는다** (Phase 2 검색 씨앗, 소급 금지).
8. **로그인 후 원래 화면·행동으로 정확히 복귀.**

### 14.2 미래 수익 가설 (Phase 2 이후, 보관)

> 본질(학습·전체 공개·콘텐츠 누적)을 해치지 않는 선에서, 사람이 충분히 모인 뒤 재검토.

- 제출 횟수 추가 (무료 한도 넉넉히 + 초과분 유료) — 단 콘텐츠 생산 마찰 주의.
- 코인 현금화 / 우승 보상 (별풍선 → 현금화 경로).
- 검색 아카이브 위의 과금 (단 *학습 콘텐츠 자체는 무료 유지* 권장 — 지난 프롬프트 블라인드 과금은 학습 충돌로 신중).
- 기업용 사내 챌린지, 광고, 명예의 전당 등 *편의·확장·자아실현* 과금.

### 14.3 Phase 2 기능 후보 (보관)

- 검색 / 카테고리 탐색 페이지
- 사용자 주제 *제안* (운영자 검수 후 개최)
- 입력 변환형 / 멀티턴("3턴 내 최고 결과") 챌린지
- 병렬 2주제 동시 운영 (사람 안정 후)
- 이미지 생성 챌린지
- 멀티 모델 (GPT/Claude 등)
- 코인 사용처 / 코인 경제
- 출석 기반 뱃지
- 다크모드

### 14.4 용어 정리

- **MVP**: 최소 기능으로 출시해 학습하기 위한 버전.
- **운영자**: 이 서비스의 유일한 관리자. 챌린지 출제·시드·모니터링 담당.
- **챌린지(Challenge)**: 하나의 과제. 제출→투표→결과의 페이즈를 가짐.
- **생성 시도(Generation)**: 한 사용자가 한 챌린지에서 프롬프트를 실행한 한 번(최대 5회).
- **제출(Submission)**: 5회 생성 중 고른 1개. 확정 잠금.
- **블라인드 투표**: 결과물만 보고 투표. 프롬프트·작성자·득표는 가림.
- **시드 제출**: 콜드 스타트 방어를 위해 운영자가 채우는 출품작.
- **별풍선 통찰**: 보상의 1차 가치는 현금이 아니라 *사회적 인정의 가시화*라는 원리.
